An adversarial read of the platform, plus real execution against a **frozen snapshot of
`db30a77`** and real SQL against the live Supabase project `gkyjfihxxdynfwqhhpyn`.

## How this was produced, and what that means for trust

**Method**

- Two sibling agents were rewriting the auth layer *while this audit ran*
  (`src/lib/supabase/*`, `src/lib/profile.ts`, `src/proxy.ts`, `src/app/layout.tsx`,
  `src/app/(app)/layout.tsx`, `next.config.ts`, `.env.example` all changed under me
  mid-session). Running `next dev` against the live working tree produced 500s on ~10 routes
  that were pure mid-edit churn (`Can't resolve '@/app/(app)/auth-actions'`). **None of those
  are reported here.**
- To get a stable target I created a detached worktree at commit `db30a77` in scratch,
  hard-linked `node_modules`, copied `.env.local`, and ran `next dev` there. Every "confirmed"
  result below comes from that snapshot, driven by Playwright (chromium at
  `/opt/pw-browsers/chromium`) with console/pageerror capture, or from `execute_sql` against
  the live database.
- Local `.env.local` has only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` —
  **no `SUPABASE_SERVICE_ROLE_KEY` and no Clerk keys**. That is not production's shape, and
  where a finding depends on that difference I say so explicitly rather than dressing a local
  misconfiguration up as a production bug.

**Two things I could not do**

1. **I could not seed test data.** Writes to the production Supabase project were blocked by
   the sandbox. The `posts` table is currently **empty** (`n_tup_ins=24, n_tup_del=21,
   n_live_tup=0`), as are `comments`, `reactions`, `poll_options`, `poll_votes`,
   `notifications` and `predictions`. So every claim below about rendering *populated* social
   content is reasoned, not executed. This is the single biggest limit on this audit.
2. **I could not reproduce the exact production `/social` failure.** See §"The `/social`
   error boundary" for what I did establish and what I ruled out.

**Severity ranking** is real user-facing breakage first, then correctness, then hygiene.
**Confidence** is stated per finding as `CONFIRMED` (I ran something and watched it fail) or
`SUSPECTED` (read from code; mechanism explained, not executed).

## C1. `/matches` renders "Something went wrong" when `SUPABASE_SERVICE_ROLE_KEY` is absent — because a public browse page reads through the service-role client with no guard

**Severity: high (fragility) · Confidence: CONFIRMED**

**Where:** `src/lib/football/last-synced.ts:30-47` (`getLastSyncedAt`), called from
`src/app/(app)/matches/page.tsx:59`, `src/app/(app)/teams/[id]/page.tsx:240,280`,
`src/app/(app)/players/[id]/page.tsx:108`, `src/app/(app)/leagues/[id]/page.tsx:60`.

**What's wrong:** `getLastSyncedAt` calls `createServiceRoleSupabaseClient()`
(`src/lib/supabase/server.ts`) unguarded. That factory does
`createClient(url, process.env.SUPABASE_SERVICE_ROLE_KEY!)`, and supabase-js **throws
synchronously** — `Error: supabaseKey is required.` — when the key is `undefined`. The throw
happens during the RSC render of a guest-viewable page, so the whole page is replaced by
`src/app/(app)/error.tsx`.

The really telling part is 25 lines further down **in the same file**:
`getTransparencyFreshness` (`last-synced.ts:62-98`) wraps the identical call in `try/catch`
with this exact comment:

> `/transparency` is guest-viewable … A `SUPABASE_SERVICE_ROLE_KEY` construction failure
> (missing env var) … must never surface as a hard crash for an ordinary visitor.

The hardening was written, understood, documented — and applied to exactly one of the two
functions. The four *most-trafficked* football pages use the unhardened one.

**Observed:**

```
=== /matches === status=200 errorBoundary=1 title="Matches | KIVO"
   [error] Error: supabaseKey is required.
       at createServiceRoleSupabaseClient (…/chunks/ssr/[root-of-the-server]__1v_4ofw._.js)
       at getLastSyncedAt (…)
```

versus, on the same run:

```
=== /transparency === status=200 errorBoundary=0 title="What KIVO knows | KIVO"
   [error] {"context":"transparency.getTransparencyFreshness","errorMessage":"supabaseKey is required."}
```

Same root cause, one page down, one page fine.

**Failure scenario:** the service-role key is rotated, mistyped, scoped to the wrong Vercel
environment, or simply not yet added to a Preview environment → `/matches`, every team page,
every player page and every league page become "Something went wrong". A *footnote* ("Fixtures
synced 4h ago") takes down the page it annotates.

**Suggested fix:** give `getLastSyncedAt` the same `try/catch → return null` treatment
`getTransparencyFreshness` already has. Better: make `createServiceRoleSupabaseClient()` itself
return `null` (or throw a typed `ServiceRoleUnavailableError`) when the key is missing, so
every one of its ~10 call sites has to decide, rather than each one silently inheriting a hard
crash. Best: reconsider reading `sync_runs` through service-role on a public page at all — a
narrow `SECURITY DEFINER` RPC returning one timestamp (the pattern already used for
`get_public_profiles`, `get_poll_results`, `get_fan_rating_summary`) fits this exactly and
removes RLS-bypass credentials from the guest render path.

## C2. `/api/health` returns a 500 with a stack trace instead of its documented 503 "unhealthy" JSON

**Severity: high · Confidence: CONFIRMED**

**Where:** `src/app/api/health/route.ts:11-25`.

**What's wrong:** the route's whole contract is "report whether the app can reach Supabase". It
opens with `const supabase = createServiceRoleSupabaseClient();` at line 12 — outside any
error handling. When the key is missing that line throws, so the endpoint whose job is to
*report* an outage instead *becomes* one. The carefully written `status: error ? 503 : 200`
branch on line 24 is unreachable in the one failure mode most likely to happen.

**Observed:** `curl localhost:3222/api/health` → `500`, with the dev log showing
`Error: supabaseKey is required. at createServiceRoleSupabaseClient (src/lib/supabase/server.ts:41:22) at GET (src/app/api/health/route.ts:12:51)`.

**Failure scenario:** an uptime monitor pointed at `/api/health` gets a 500 with an HTML/stack
body rather than `{"status":"unhealthy","checks":{"database":"unreachable"}}`. Any monitor
parsing the documented JSON shape breaks; the alert says "500" rather than "database
unreachable".

**Suggested fix:** wrap the client construction and the query in one `try/catch` and return the
503 body from the catch. This is a 4-line change and it is the difference between an honest
health endpoint and a decorative one.

## C3. `src/lib/rate-limit.ts` claims to "fail open on infra errors" — it does not fail open on the most likely infra error

**Severity: high (fragility) · Confidence: CONFIRMED (same mechanism as C1/C2, verified via `/api/health`)**

**Where:** `src/lib/rate-limit.ts:35` inside `checkRateLimit`, documented at lines 26-27:

> Fails open on infra errors (a Supabase hiccup shouldn't lock users out of the app) but fails
> closed on the actual over-limit case.

**What's wrong:** the fail-open handling (`if (countError) { … return { ok: true } }`, line 45)
only covers a *query* error. `createServiceRoleSupabaseClient()` on line 35 runs first and
throws before any query exists. `checkRateLimit` is called by `createPost`, `createPoll`,
`voteOnPoll`, `setReaction`, `createComment`, `toggleSave`, `toggleFollow`,
`submitPrediction`, `submitFanRating`, `searchPlatform`, `setGameweekRoster`,
`joinFantasyLeague` — i.e. essentially every write in the product. Without the service-role
key, all of them throw an unhandled exception on the *first line of real work* rather than
degrading.

**Failure scenario:** service-role key missing/rotated → every social write, every prediction,
every save and every search throws a Server Action error, and the client components that call
them (`SaveButton`, `FollowButton`, `PostComposer`, …) show either nothing or a generic
failure. The documented graceful degradation never engages.

**Suggested fix:** same as C1 — make the factory's failure mode explicit and handle it once.

## C4. `/social` hits the error boundary the moment `<ClerkProvider>` is not mounted, because `useSupabaseClient()` calls `useSession()` unconditionally

**Severity: high (at `db30a77`) · Confidence: CONFIRMED (reproduced locally)**

> **Read the caveat.** This reproduces in an environment where Clerk is *unconfigured*, which
> production was not. I am reporting it because (a) it is the only mechanism I found that makes
> `/social` specifically — and no other page — hit the boundary, and (b) it is a real structural
> coupling that survives conceptually into the Supabase-Auth rewrite. See §"The `/social` error
> boundary" for the full reasoning and what I ruled out.
>
> **Status as of commit `fd82c95` ("Move authentication from Clerk to Supabase Auth"), which
> landed while this audit was being written:** the specific `useSession()` throw is **gone** —
> `src/lib/supabase/client.ts` now uses `createBrowserClient` from `@supabase/ssr` with no React
> context dependency. The *class* of bug survives in a narrower form: line 20-23 is
> `createBrowserClient(process.env.NEXT_PUBLIC_SUPABASE_URL!, process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!)`,
> and `createBrowserClient` throws `supabaseUrl is required` on an empty string. Those are
> build-time-inlined public env vars, so a Preview deployment missing either one produces exactly
> the same signature — server `200`, client throw, `/social` and every realtime-mounting page at
> "Something went wrong". The mitigation in the fix note below still applies verbatim.

**Where:** `src/lib/supabase/client.ts:13-25` (at `db30a77`) →
`src/components/social/social-feed.tsx:41`.

**What's wrong:** `useSupabaseClient()` calls Clerk's `useSession()` with no provider check.
Clerk's hook **throws** — not returns undefined — when no `<ClerkProvider>` ancestor exists.
The root layout at `db30a77` mounts the provider **conditionally**
(`{clerkConfigured ? <ThemedClerkProvider>{app}</ThemedClerkProvider> : app}`, `src/app/layout.tsx`),
gated on a **server-only** check (`isClerkConfigured()` requires *both*
`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY`). So there is a real configuration
in which the client tree renders without the provider while client components still call the
hook.

`/social` is uniquely exposed: `SocialFeed` calls `useSupabaseClient()` on **every** render,
regardless of whether there is any data. The app's other consumers (`useRealtimeFixtures` via
`LiveFixtureList`, `useRealtimeRoomPosts` via Match Room) only mount when there are fixtures or
a Room to show — which, with an empty `fixtures` table, there weren't.

**Observed** (guest, no session, snapshot at `db30a77`):

```
=== /social === status=200 errorBoundary=1 title="Social | KIVO"
   [error] Error: useSession can only be used within the <ClerkProvider /> component.
=== /home  === status=200 errorBoundary=0
=== /live  === status=200 errorBoundary=0
=== /teams === status=200 errorBoundary=0
```

Note `status=200`: the **server** rendered the page fine and the **client** threw during
hydration. That is exactly the shape of the reported production bug — a page that looks healthy
in server logs but shows "Something went wrong" to the user — and it explains why a previous
investigation "found no reproduction" if it only checked server-side rendering.

**Suggested fix (for whichever auth layer wins):** the data-client hook must never be able to
throw. Either derive the token from a source that has no React-context precondition (which the
`@supabase/ssr` browser client the siblings are moving to does), or guard the hook. And
independently: a *live-update convenience* should never be able to take down a whole page —
wrap `SocialFeed`'s realtime subscription in its own error boundary or a `try/catch`, so the
feed degrades to "no live pill" rather than to "Something went wrong".

## The `/social` error boundary — what I established, and what I ruled out

The production screenshot showed `/social` at "Something went wrong" for a signed-out visitor.
I could not reproduce **that exact failure**, and I would rather say so than hand someone a
plausible-sounding story to chase. Here is the full state of the investigation.

**Established:**

- `/social` **can** reach the error boundary while the server returns `200`, because the failure
  is a client-side throw during hydration (C4). Any investigation that only inspected server
  logs or response codes would correctly conclude "no reproduction" and still be wrong. That
  alone is worth knowing.
- `/social` is the **only** page in the app whose client tree calls `useSupabaseClient()`
  unconditionally. Every other consumer is behind data that may be absent. So "only `/social`
  breaks" is a signature that fits this component and not the others.
- Two independent hydration-mismatch generators are densest on `/social`: `timeAgo` on every
  post card and every comment row (C5).

**Ruled out by direct query against the live database:**

- *A null/missing author profile.* `posts.ts:241-243` already falls back to `"KIVO fan"` and
  `null` avatar. It cannot throw. `resolveAvatarSrc` is total over its input.
- *`get_public_profiles` returning fewer rows than requested.* Handled by the same fallback.
  The one live profile with `avatar_type='kivo'` but `avatar_kivo_id = null` (`kivo_system`)
  resolves cleanly to `null` through `isKivoAvatarId`.
- *A poll with options but no results.* `get_poll_results` is a `LEFT JOIN` (verified via
  `pg_get_functiondef`), so a zero-vote poll returns one row per option with `vote_count = 0`,
  not an empty set. `PollBlock` guards its percentage with `total > 0`. No divide-by-zero, no
  crash. (The RPC *erroring* is a different, real problem — S5.)
- *RLS blocking a guest.* Confirmed via `pg_policies` that `posts_select_public`,
  `comments_select_public`, `reactions_select_public` and `poll_options_select_public` all
  include the `anon` role, and that every function their `USING` clauses call
  (`private.effective_moderation_status_for`, `private.current_profile_id`, `private.is_admin`)
  is `EXECUTE`-able by `anon`. Running `set local role anon; select count(*) from posts;`
  succeeded. A guest read cannot raise "permission denied".
- *The shadow-mute filter from `0045`.* It is a `IS DISTINCT FROM` comparison against a
  `SECURITY DEFINER` function that returns `NULL` for an unreadable profile, and `NULL IS
  DISTINCT FROM 'shadow_muted'` is `true`. It fails **open**, so it cannot hide or break a row
  unexpectedly.
- *The `is_system` column from `0047`.* `is_system` is `NOT NULL` with a default and is filtered
  with `.eq("is_system", false)` only on the non-fixture path. Nothing dereferences it unsafely.

**Not ruled out, and untestable from here:**

- The `posts` table is currently **empty** (24 rows ever inserted, 21 deleted). Whatever data
  was on screen in that screenshot is gone, and I was not permitted to seed replacements. If the
  crash was data-shaped, the evidence has already been deleted.
- `getOrCreateProfile()` at `db30a77` calls Clerk's `currentUser()`, which performs a Backend API
  round trip for a signed-in request. A Clerk outage or rate-limit there would throw and take out
  every `(app)` page — but that would not be `/social`-specific, and the report was `/social`-specific.

**What would settle it:** wire an error reporter (Sentry or equivalent) to `src/app/error.tsx`
and `src/app/(app)/error.tsx:32-36`, which today do nothing but `console.error(error)` behind a
comment reading *"No error-tracking service wired up yet — that's a separate decision."* Until
that decision is made, every production error boundary is a screenshot and a guess. Given the
founder is fielding these one at a time from users, this is probably the highest-leverage
non-bug item in this document.

## C5. Every date rendered by a client component diverges between server HTML and browser — a guaranteed hydration mismatch for every non-`en-US` visitor

**Severity: medium-high · Confidence: CONFIRMED (divergence demonstrated by execution)**

**Where:** `src/lib/format.ts` — `formatDate` (line 44-49), `formatClockTime` (line 36-38),
`timeAgo`'s >30-day branch (line 16-17). All three pass `undefined` as the locale, i.e. "use
whatever locale this runtime defaults to".

Called from these **client** components, which Next.js server-renders *and then hydrates*:

| Function | Client call site |
| --- | --- |
| `formatDate` | `src/components/transfers/transfers-list.tsx:97` |
| `formatClockTime` | `src/components/ai/chat.tsx` |
| `timeAgo` | `src/components/social/post-card.tsx:390`, `src/components/social/comment-thread.tsx:40`, `src/components/layout/notification-bell.tsx:172`, `src/components/notifications/notifications-list.tsx`, `src/components/ai/conversation-history.tsx` |

**What's wrong:** the server runtime resolves `undefined` to Node's default locale; the browser
resolves it to the user's. Those produce different strings, so React's hydration compares
different text.

**Observed** (`node` in this environment, i.e. what SSR produces vs. what a browser would):

```
en-US  formatDate: August 14, 2026   | short: Aug 14, 2026   | clock: 10:30 AM
en-GB  formatDate: 14 August 2026    | short: 14 Aug 2026    | clock: 10:30
de-DE  formatDate: 14. August 2026   | short: 14. Aug. 2026  | clock: 10:30
fr-FR  formatDate: 14 août 2026      | short: 14 août 2026   | clock: 10:30

node default (what SSR uses):  August 14, 2026 / 10:30 AM
Intl default locale: en-US
```

`timeAgo` has a second, locale-independent version of the same bug: it reads `Date.now()`. A
post created 59 seconds before the server render is `"just now"` in the HTML and `"1m"` by the
time the browser hydrates.

**Failure scenario:** a UK user opens `/transfers`. Server HTML says `Aug 14, 2026`; the client
renders `14 Aug 2026`. React logs a hydration error and discards the server-rendered subtree in
favour of a client re-render — losing the SSR benefit, flashing content, and (in dev) throwing
the Next.js error overlay. On `/social`, *every post card and every comment* carries a
`timeAgo` value, so the density of mismatch is highest exactly on the page that was reported as
broken.

**There is a second, non-hydration bug hiding in the same place:** the *server*-rendered call
sites (`src/app/(app)/players/[id]/page.tsx:229,416`, `src/app/(app)/teams/[id]/page.tsx:716`)
resolve to the **server's** locale for everybody. So a UK user sees `August 14, 2026` on a
player page and `14 Aug 2026` on `/transfers` — the same date, two formats, in one app.

**Suggested fix:** pick one policy and enforce it.
- For SSR-stable output: pass an explicit locale (`"en-GB"`), so server and client agree and
  every user sees the same thing.
- For per-user locale: render these client-side only — `suppressHydrationWarning` on the
  element, or a `useSyncExternalStore`-style "not until hydrated" gate like `ThemeProvider.ready`
  already implements, or `<time dateTime={iso}>` with the text filled in after mount.

`timeAgo` additionally needs the `Date.now()` read to be hydration-safe regardless of locale.

## C6. `/u/<username>` resolves the profile **twice** per request, and turns any infra failure into a fake 404

**Severity: medium · Confidence: CONFIRMED (duplicate call observed; 404 path read)**

**Where:** `src/app/(app)/u/[username]/page.tsx:44-63` (`getPublicProfile`), called from
`generateMetadata` (line ~70) and again from `PublicProfilePage` (line 89).

**Two problems:**

1. **Duplicate work.** `getPublicProfile` is a plain `async function`, not wrapped in React's
   `cache()` — unlike `getOrCreateProfile` (`src/lib/profile.ts:25`) and
   `createServerSupabaseClient` (`src/lib/supabase/server.ts:23`), both of which carry long
   comments about exactly this. So every profile page view makes **two** `get_public_profile_by_username`
   round trips.

   **Observed:** the console captured `Failed to resolve public profile` **twice** for a single
   `GET /u/nobody`:

   ```
   === /u/nobody === status=200 errorBoundary=0
      [error] Failed to resolve public profile  {message: Error: …}
      [error] Failed to resolve public profile  {message: Error: …}
   ```

2. **Misleading empty state.** Line 46-49 collapses *every* error into `return null`, and line
   90 turns `null` into `notFound()`. A transient database error, a JWKS blip, or a Supabase
   outage therefore renders **"this profile doesn't exist"** for a profile that does exist —
   and returns a 404, so search engines and shared links can get poisoned by a momentary
   outage.

**Suggested fix:** wrap `getPublicProfile` in `cache()` (one line, matching the established
convention). Separate "RPC returned zero rows" (→ `notFound()`) from "RPC errored" (→ rethrow,
so the error boundary tells the truth, or render an explicit "couldn't load this profile" state).

## C7. CSP blocks the Vercel Analytics dev script on every page

**Severity: low (dev-only) · Confidence: CONFIRMED, *and* confirmed **not** to affect production**

**Where:** the `script-src` directive in `next.config.ts` (line 70 as of `eec37a7`) vs
`src/app/layout.tsx` (`<Analytics />`). Still present after the Supabase Auth migration rewrote
this file — the Clerk hosts were removed from `script-src`, the analytics host was never added.

**What's wrong:** the CSP block carries this comment (`next.config.ts:66-67` as of `eec37a7`):

> No analytics/tracking script is wired in anywhere (checked package.json and grepped the app
> for gtag/posthog/segment/etc — none present).

That statement is false. `@vercel/analytics` **is** in `package.json` and `<Analytics />` **is**
mounted in the root layout. `script-src` has no entry for `va.vercel-scripts.com`, so the
browser refuses the script.

**Observed** on *every single route* probed (18 of them):

```
[error] Refused to load the script 'https://va.vercel-scripts.com/v1/script.debug.js'
        because it violates the following Content Security Policy directive:
        "script-src 'self' 'unsafe-inline' https://*.clerk.accounts.dev https://challenges.cloudflare.com 'unsafe-eval'"
```

**Why this is *low* and not high — I checked before reporting:**
`node_modules/@vercel/analytics/dist/next/index.mjs:84-94` (`getScriptSrc`) returns
`https://va.vercel-scripts.com/v1/script.debug.js` **only** when `isDevelopment()`; in
production it returns the same-origin `/_vercel/insights/script.js`. So the root layout's claim
that "no CSP change is needed" is correct *for production*, and analytics is not broken in prod.
I nearly filed this as a production outage; it is not one.

**Real cost:** a red CSP error on every page in local dev, which is exactly the noise that makes
a genuine console error (like C4's `useSession` throw) easy to miss. The stale comment at
`next.config.ts:59-60` will also mislead the next person to touch the CSP.

**Suggested fix:** correct the comment, and add `https://va.vercel-scripts.com` to `script-src`
under the existing `isDev` conditional (the same shape `'unsafe-eval'` already uses).

## C8. Two `private.*` functions have no explicit grant, so `PUBLIC` (and therefore `anon`) holds `EXECUTE`

**Severity: low · Confidence: CONFIRMED (queried live)**

**Where:** live project `gkyjfihxxdynfwqhhpyn`.

This is the same class of bug migrations `0025` and `0050` were written to fix — Postgres grants
`EXECUTE` to `PUBLIC` by default on every new function unless a migration revokes it.

```sql
select proname, prosecdef, proacl from pg_proc p
  join pg_namespace n on n.oid = p.pronamespace where n.nspname = 'private';
```

| function | `SECURITY DEFINER` | `proacl` | `anon` has EXECUTE |
| --- | --- | --- | --- |
| `private.can_moderate()` | **yes** | `NULL` (default → PUBLIC) | **true** |
| `private.set_poll_vote_post_id()` | no (trigger fn) | `NULL` (default → PUBLIC) | true |

Every other `private.*` function has an explicit ACL (`{=X/postgres, postgres=X/postgres,
authenticated=X/postgres, anon=X/postgres}`) — so this is an oversight, not a policy.
`has_schema_privilege('anon','private','USAGE')` is also `true`.

**Why it's low, honestly:** the `private` schema is not in PostgREST's exposed schema list, so
`anon` cannot reach these over `/rest/v1/rpc/`. `can_moderate()` also reads only the caller's
own role, so calling it as `anon` returns `false`. This is defence-in-depth erosion, not a live
exploit — but it is the exact drift the `0025`/`0050` pattern exists to prevent, and it will
keep recurring until there is a `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA private FROM PUBLIC`
plus `ALTER DEFAULT PRIVILEGES` in a migration.

**Also flagged live by `get_advisors(security)`** (not new bugs, listed so nobody re-derives them):
`public.rate_limit_events` has RLS enabled with zero policies (this is **intentional and correct** —
see `src/lib/rate-limit.ts:20-24`; the advisor's INFO can be dismissed), and 11 `public.*`
`SECURITY DEFINER` functions are `anon`-executable. I checked each of the `anon`-reachable ones
against its definition — `get_public_profiles`, `get_public_profile_by_username`,
`get_poll_results`, `get_fan_rating_summary`, `get_prediction_consensus`,
`get_predictions_leaderboard`, `get_most_followed_teams`, `get_fantasy_ownership`,
`is_username_available` — and every one returns only data the app already renders publicly.
**No RLS bypass found.** They are deliberately narrow, which is the right design.

## S1. "Save" and "Follow" are the dead buttons — they swallow every server error silently

**Severity: high (this is almost certainly the reported "buttons appear dead") · Confidence: SUSPECTED (deterministic from code; not executed because it needs a signed-in session)**

**Where:** `src/components/ui/save-button.tsx:45-53` and
`src/components/ui/follow-button.tsx:51-59`.

```ts
// save-button.tsx:45-53
startTransition(async () => {
  const result = await toggleSave(targetType, targetId, previous);
  if (result.error) {
    setSaved(previous);          // ← revert, and that is all
  } else { … }
});
```

`result.error` is **read and discarded**. There is no `setError`, no toast, no `role="alert"`.
The button optimistically flips, then flips back, with zero explanation.

The rest of the app does this correctly, which is what makes these two stand out:

| control | on error |
| --- | --- |
| `ReactionPicker` (`reaction-picker.tsx:102-109`) | reverts **and** `setError`, shown in a `role="alert"` that auto-clears after 4s |
| `PollBlock` (`post-card.tsx:142-146`) | reverts **and** `setError`, rendered inline |

## S2. The notification badge very likely snaps back to its old count after "Mark all read"

**Severity: medium-high · Confidence: SUSPECTED — I could not test it (no auth locally, `notifications` table empty) and the outcome depends on Next 16 Server-Action revalidation semantics I did not verify empirically**

**Where:** `src/components/layout/notification-bell.tsx:66-69, 134-140` and
`src/app/(app)/notifications/actions.ts:25, 44`.

**The mechanism:** the bell holds its state in `useOptimistic`, whose *base* value is the
`initialUnreadCount` **prop**. `useOptimistic` discards the optimistic value the instant the
transition that produced it settles, reverting to that base. So for the badge to stay at 0
after "Mark all read", the component's props must have been refreshed by then.

`markAllNotificationsRead` calls `revalidatePath("/notifications")`. But `NotificationBell` is
rendered by `AppShell` from `src/app/(app)/layout.tsx` — the **layout**, not the
`/notifications` page. The code comment at `actions.ts:22-25` records that this was deliberately
narrowed:

> Was `revalidatePath("/", "layout")`, which dropped the entire app's cache…

That narrowing removed the one revalidation that would have re-rendered the layout the bell
lives in.

**Expected symptom:** on any page other than `/notifications`, click the bell → "Mark all read"
→ badge drops to 0 → transition settles → badge pops back to the old number. Worse,
`handleMarkAllRead` (line 135) and `handleItemClick` (line 126) both do
`setFocusSyncedUnreadCount(null)`, deliberately throwing away the fresher count the
focus-listener at line 95-108 had fetched — so the fallback that could have masked this is
switched off precisely when it is needed.

**Why I am not calling it confirmed:** whether a Server Action's `revalidatePath` for a
*different* path still causes the router to refetch the current route (and hence re-render the
layout) is Next-version-specific, and I did not verify it on 16.3.1. If Next refetches the
current URL wholesale, the layout re-renders and the badge is fine.

**How to settle it in 60 seconds:** sign in on a build with ≥1 unread notification, sit on
`/social`, click "Mark all read", and watch the badge. If it comes back, the fix is either
`revalidatePath("/(app)", "layout")` or — cheaper and more surgical — have the action return
the new count and store it in `focusSyncedUnreadCount` instead of nulling it.

## S3. "Load more" on `/social` skips exactly one post after a notification deep-link

**Severity: medium · Confidence: SUSPECTED (deterministic arithmetic; not executed — the `posts` table is empty)**

**Where:** `src/app/(app)/social/page.tsx:29-33` and
`src/components/social/social-feed.tsx:126`.

**What's wrong:** `page.tsx` **prepends** a deep-linked post that wasn't on page one:

```ts
// page.tsx:30-33
if (targetPostId && !pageOne.some((p) => p.id === targetPostId)) {
  const { posts: targetPosts } = await fetchPostsPage(0, profile?.id ?? null, { postIds: [targetPostId] });
  if (targetPosts.length > 0) posts = [...targetPosts, ...pageOne];
}
```

`SocialFeed` then paginates with `loadMorePosts(posts.length, …)` (line 126) — using array
length as a server offset. After a prepend, `posts.length === 21` while the server has served
offsets `0..19`. Requesting offset 21 **skips the post at offset 20** permanently: it is never
reachable by any amount of "Load more".

**Failure scenario:** user taps a notification → lands on `/social?post=<id>` for an older post →
scrolls → "Load more" → one post silently missing from the feed forever.

**Two related offset-pagination issues in the same component:**
- Any post created between the initial render and a "Load more" shifts the window, so a post
  already on screen is returned again → a duplicate card **and** a React duplicate-`key` warning
  (`social-feed.tsx:188` keys on `post.id`).
- `handleShowNewPosts` (line 140-153) calls `loadMorePosts(0, …)` and **replaces** `posts`
  wholesale. A reader who had loaded 5 pages loses all 100 posts back to 20, with no indication
  that happened.

**Suggested fix:** track a real `serverOffset` in state, incremented by `result.posts.length`,
independently of what's in the array; or move to keyset pagination on `created_at` (the feed is
already strictly `created_at DESC`, so `.lt("created_at", oldest)` is a drop-in that fixes the
skip, the duplicate and the "new post shifts the window" problem at once).

## S4. Dropping your fantasy captain silently leaves the squad with no captain

**Severity: medium · Confidence: SUSPECTED (read from code; no fantasy data to exercise)**

**Where:** `src/app/(app)/fantasy/actions.ts:196-231` (`setGameweekRoster`).

```ts
const captainId     = existingRoster?.find((r) => r.is_captain)?.player_id;      // :202
const viceCaptainId = existingRoster?.find((r) => r.is_vice_captain)?.player_id; // :203
const toRemove      = [...existingIds].filter((id) => !newIds.has(id));          // :206
…
is_captain:      pick.playerId === captainId,                                    // :226
is_vice_captain: pick.playerId === viceCaptainId,                                // :227
```

`captainId` is read from the **old** roster. If the captain is one of the players being dropped,
`captainId` names a player who appears in none of the new `rows`, so `is_captain` is `false`
for every pick. `validateRoster` (`fantasy-rules.ts`) does not require a captain, so the save
succeeds with no error and no warning.

**Failure scenario:** manager swaps out their captain for a new signing, hits Save, gets a
success state — and plays the gameweek with nobody's points doubled. `fantasy-scoring.ts:39-48`
confirms doubling depends entirely on `is_captain` / `is_vice_captain`, so this is real points
lost.

**Partial mitigation, which is why this is medium and not high:** `fantasy-builder.tsx:453`
does render *"No captain selected — their points won't be doubled this gameweek."* So the state
is discoverable — but only after a re-render, and the save itself gives no hint that it just
cleared the captaincy.

**Also in the same function — a non-atomic write:** lines 208-217 `DELETE` the dropped picks,
then lines 229-232 `UPSERT` the new ones. If the upsert fails, the delete has already committed:
the user gets *"Couldn't save your squad. Try again."* while their roster has silently lost
players. Same shape exists in `voteOnPoll` (`social/actions.ts:180-192`) and `setReaction`
(`:219-242`) — delete-then-insert with no transaction, so a failed insert leaves the user with
*no* vote/reaction rather than their previous one.

**Suggested fix:** promote the vice-captain (or fall back to the highest-priced remaining
starter) when the captain is dropped, and surface it — "Your captain was transferred out;
`<name>` is now captain." For atomicity, move the roster write into a `plpgsql` `SECURITY
DEFINER` RPC so delete+insert share a transaction, matching the pattern
`join_public_fantasy_league` / `redeem_invite_code` already establish in this codebase.
