# KIVO Next Gen

An ambitious, grounded proposal for what KIVO becomes next: new features, frontend and backend upgrades, a deep pass on UX and flow, and a real bug hunt.

## How this document was produced

Read in full before a single item below was written: `KIVO_BUILD_ACKNOWLEDGEMENT.md` (the founding brief in the founder's own terms), all 895 lines of `RECOMMENDATIONS.md` (20 sections, ~320 items, a large share marked RESOLVED in the last 48 hours), `docs/STRUCTURAL_SURVEY.md`, `BUILD_STATUS.md`, `HANDOFF.md`, `ARCHITECTURE.md`, `DECISIONS.md`, and then the code itself — every route under `src/app/(app)/`, the `/admin` tree, the API routes, the component library, `src/lib/` (football pipeline, AI grounding, rate limiting, notifications, rewards, theme), the config (`next.config.ts`, `vercel.json`, `package.json`), and all 53 files under `supabase/migrations/`.

**Every item names the real file, table, RPC, column or migration it touches.** Where a line number appears, it was read this session. Where an idea would need data KIVO does not have, it is marked **NOT BUILDABLE** with the specific reason, rather than quietly proposed and quietly dropped later.

### Relationship to `RECOMMENDATIONS.md`

`RECOMMENDATIONS.md` is the running backlog and is owned by other agents right now. This document deliberately does **not** re-propose anything already shipped or already open there. Where an item here extends an existing one, it cites it by number and states exactly what is new. A handful of items exist specifically because two separately-shipped RECOMMENDATIONS items interact badly with each other — those are called out as regressions between passes, not as new features.

### Conventions

- **Size**: **Small** (under a day), **Medium** (a few days), **Large** (a week or more, or schema + UI + pipeline).
- Item ids are prefixed `KN-` so they never collide with `RECOMMENDATIONS.md`'s 1–320.
- Standing rules respected throughout: zero fabricated football data; no invented engagement signals; no outcome prediction (see `RECOMMENDATIONS.md` item 246 — this platform explains, it does not forecast results); no fake social proof.

### The auth context this document was written against

The founder has decided to remove Clerk entirely, move to **Supabase Auth (email OTP only, no social login)**, and **gate the whole app behind auth — no guest preview**. That work is in flight in sibling sessions as this is written: `supabase/migrations/0053_supabase_auth_identity.sql` (adds `profiles.auth_user_id`, rewrites `private.current_profile_id()` / `current_role()` / `current_moderation_status()` / `current_moderation_raw_snapshot()` to `auth_user_id = auth.uid()`, rewrites the three `profiles` policies and the three `avatars` storage policies, drops `private.current_clerk_user_id()`), `@supabase/ssr` in `package.json`, a cookie-based `createServerSupabaseClient()` in `src/lib/supabase/server.ts`, a rewritten `getOrCreateProfile()` in `src/lib/profile.ts`, and `docs/email-templates/`.

Nothing below proposes a Clerk improvement. Section 6 is entirely about what that migration leaves behind, and it is grounded in the migration file, `src/lib/auth.ts`, `src/lib/auth-actions.ts`, `src/app/sign-in/page.tsx` and the rewritten `(app)/layout.tsx` as they stood when this was read — not in guesses about them. Three items in that section were rewritten mid-session as sibling commits landed; where `RECOMMENDATIONS.md` items 321–323 now cover a gap this document had also found, it is cited rather than duplicated.

## 1. Bug hunt

Real defects found by reading the code this session. Each names the file and why the behaviour is wrong, not just that it looks odd. Several are **regressions between two separately-shipped `RECOMMENDATIONS.md` items** — the most valuable kind to find, because each pass verified its own change in isolation and neither could see the interaction.

### 1a. Shipping-now breakage

**KN-1. The Content-Security-Policy blocks every remote team crest and player photo in the app.** `next.config.ts`'s `img-src` directive is `'self' data: blob: https://img.clerk.com` plus the Supabase origin — `media.api-sports.io` is not in it. (The Clerk avatar host was deliberately kept for legacy `profiles.avatar_url` rows, per `RECOMMENDATIONS.md` item 322 — so the directive has been reviewed recently and the football provider host is still missing from it.) That would be harmless if crests went through Next's image optimizer (a same-origin `/_next/image` request), but `RECOMMENDATIONS.md` item 86's fix added `unoptimized` to exactly these components: `src/components/ui/team-crest.tsx:40`, `src/components/ui/player-avatar.tsx:33`, `src/app/(app)/fantasy/pitch.tsx:74`, `src/components/layout/mobile-bottom-nav.tsx:109`. `unoptimized` means the browser fetches the provider URL directly, which is precisely what `img-src` governs. Item 86 (image perf) and item 201 (security headers) were shipped in different passes; each is individually correct and together they mean no club crest renders in production. Fix: add the provider image hosts to `img-src` alongside `remotePatterns`, derived from one shared constant so the two lists cannot drift again. **Small, and the highest-severity item in this document.**

> **BUILT (2026-08-18).** Partly already fixed when this was picked up: commit `c4f6222` had added `https://media.api-sports.io` to `img-src`, so the acute breakage was gone. The structural half — "derived from one shared constant so the two lists cannot drift again" — was not, and that is the part that keeps it fixed. `src/lib/football/image-hosts.ts` is now the single source for both `images.remotePatterns` and the CSP `img-src`, with a unit test that fails if they are ever derived differently. Verified empirically in Chromium against the real response header by listening for genuine `securitypolicyviolation` events: `media.api-sports.io` loads with no violation, an unlisted host is `BLOCKED by img-src` — so the policy is really enforced and the pre-`c4f6222` state really did block every crest.

**KN-2. `next.config.ts`'s `images.remotePatterns` allows exactly one host, so selecting the second provider breaks the Standings tab.** The only entry is `media.api-sports.io`. `StandingsTab` in `src/components/matches/match-centre-tabs.tsx` renders `<Image src={row.crestUrl} width={16} height={16} />` **without** `unoptimized` — the one crest render in the app that still goes through the optimizer, which hard-errors on a host that is not in `remotePatterns`. `FOOTBALL_DATA_PROVIDER=thesportsdb` is a real, documented, implemented configuration (`src/lib/football/providers/thesportsdb.ts`, `docs/PROVIDER_ABSTRACTION.md`) and its normalizer maps `strHomeTeamBadge`/`strAwayTeamBadge` (`thesportsdb-normalizers.ts:133,139`) — URLs on a completely different host. Switching providers therefore breaks Match Centre. Fix: use `TeamCrest` here like every other call site, and make `remotePatterns` cover every provider the abstraction actually supports. **Small.**

> **BUILT (2026-08-18).** Two corrections to the item as written. First, the throw is development-only (`node_modules/next/dist/shared/lib/image-loader.js` guards it with `NODE_ENV !== 'production'`); in production an unconfigured host is a 400 from `/_next/image`, so it is a broken crest on every standings row rather than a crash — still a real defect, just a different one. Second, `StandingsTab` was not the only optimizer-bound remote image: `leagues-list.tsx`, `leagues/[id]/page.tsx` and `recently-viewed-strip.tsx` had the same coupling and are fixed too. Standings now renders `TeamCrest`; the two competition surfaces render a new shared `CompetitionLogo` (`src/components/ui/competition-logo.tsx`, the third member of the TeamCrest/PlayerAvatar family, which also settles the Shield-vs-Trophy inconsistency between the list and the page it links to); the recently-viewed strip renders `unoptimized`. No remote provider image in the app goes through the optimizer any more, so `remotePatterns` can no longer gate whether a page renders.
>
> `remotePatterns` covering "every provider the abstraction supports" was **not** done as written, deliberately. TheSportsDB's image host is genuinely unknown here — thesportsdb.com is refused by this environment's egress proxy (403 to CONNECT, confirmed this session), so no badge URL has ever been read off a real response, and a guessed hostname would be exactly the kind of unverified claim this product's first rule forbids. It is configuration instead: `FOOTBALL_IMAGE_HOSTS` (documented in `ENVIRONMENT.md` next to `FOOTBALL_DATA_PROVIDER`) feeds both lists, rejects anything that isn't a bare hostname since the value lands verbatim in a security header, and was verified end-to-end in Chromium — `r2.thesportsdb.com` blocked without it, allowed with it, `*.evil.example` dropped with a build-log warning.

**KN-3. `vercel.json` no longer schedules the cron worker, but `BUILD_STATUS.md` still says it runs every minute.** `vercel.json` is now `{ "$schema": ... }` and nothing else (the `crons` array was removed in commit `771ba83` so Hobby-plan deploys succeed). `src/app/api/cron/sync-live/route.ts` — an adaptive, quota-aware, dedup-aware, well-tested worker — is therefore unreachable in production, while `BUILD_STATUS.md`'s "Automated server-side live worker (cron)" row reads "fired every minute by Vercel Cron (`vercel.json`)". That is now a false claim in the one document written specifically to be honest about what works. Fix the doc immediately; separately decide the real trigger (see KN-99). **Small for the doc.**

> **BUILT (2026-08-18).** `BUILD_STATUS.md`'s worker row now leads with "**ROUTE BUILT — NOT SCHEDULED.** Nothing invokes it in production today", says why (`vercel.json` carries no `crons` array; Hobby rejects a sub-daily schedule) and what re-enabling it takes. A second false claim in the same file was fixed alongside it: the Notifications row asserted "one real scheduled job... fires unconditionally on its own minute-by-minute schedule", which was the same wrong belief stated as background fact. `ENVIRONMENT.md` and `docs/LIVE_DATA.md` were re-read and were already honest — the drift was confined to `BUILD_STATUS.md`. Choosing the real trigger is KN-99, outside this queue's range and left to it.

**KN-4. `syncTodayFixtures` can leave a `sync_runs` row stuck in `running` forever, and that row then suppresses the cron worker.** `src/lib/football/sync.ts` inserts a `sync_runs` row with `status: "running"` at the top, then only wraps `getFixturesByDate()` in try/catch. Everything after it can throw straight out of the function: `batchFindMappedIds` rethrows any PostgREST error, and the prior-status lookup does a bare `if (priorError) throw priorError`. On that path the run row is never updated — Data Health shows a phantom in-progress sync permanently, and `src/app/api/cron/sync-live/route.ts`'s dedup query (`status = 'running'`, `trigger_source = 'cron'`) treats it as live work for `DEDUP_WINDOW_MINUTES`. Fix: wrap the whole body in try/catch/finally so the run row always reaches a terminal status. **Small.**

> **BUILT (2026-08-18).** `syncTodayFixtures` now routes every terminal write through one `finalizeRun` funnel called from the success path, from a catch, and from a `finally` that only fires if neither of those got there — the row cannot be left `running` by any exit the function has. Two things came free with the funnel: `provider_quota_remaining` and `raw_response_sample` are now written on *every* terminal path rather than only the two that used to, which is precisely the case an admin most needs them for (a run that died part-way), and `records_processed` survives a mid-run throw instead of being reported as 0.

**KN-5. `/live` decides its own section layout on the server, then mutates rows on the client via Realtime.** `src/app/(app)/live/page.tsx` computes `hasLiveFixtures` at render time and shows *either* a "Live now" block *or* a "Today's fixtures" block. `useRealtimeFixtures` (`src/hooks/use-realtime-fixtures.ts`) then pushes status changes into whichever list was rendered. So a fixture that kicks off while a user is sitting on `/live` flips its badge to LIVE inside the "Today's fixtures" card and never moves into "Live now"; the reverse leaves a finished match sitting under "Live now" until a reload. The realtime plumbing works; the page's structure is a server-time snapshot. Fix: render one list and let the client partition it from live status. **Small.**

> **BUILT (2026-08-18).** `/live` now fetches one merged set (the two queries stay, because "what is in play" is not date-bounded and "what is on today" is) and hands it to `LiveCentreSections`, which partitions on current status every render. `LiveFixtureList` was the wrong place for the subscription once two sections share one list — two independently-subscribed lists could not have moved a fixture between them — so it is now the presentational `FixtureGroups` and the single subscription lives one level up. One thing changed beyond the stated fix: the sections render **together** rather than either/or. Hiding the rest of today the moment one match kicks off was never a decision, it fell out of the either/or structure, and "what's on later" is exactly what someone watching a live match wants next.

**KN-6. `useRealtimeFixtures` subscribes to every `fixtures` UPDATE site-wide.** `src/hooks/use-realtime-fixtures.ts` registers `{ event: "UPDATE", schema: "public", table: "fixtures" }` with no `filter`, then discards non-matching ids client-side. On a broad sync day that is every fixture in the database pushed over the websocket to every connected client, on a product whose stated launch market is mobile-network-constrained. `src/hooks/use-realtime-room-posts.ts` already does this correctly with a server-side `filter: fixture_id=eq.<id>`. Fix: an `id=in.(...)` filter, or subscribe per competition. **Small.**

> **BUILT (2026-08-18).** Server-side `id=in.(…)` filters, chunked at 40 ids across several bindings on one channel rather than one unbounded filter string — the watched set is a whole page of fixtures and the Realtime server parses and evaluates that filter on every change. Verified against `@supabase/realtime-js`' own type definitions that `in` is one of the operators Realtime actually evaluates server-side (its `RealtimePostgresChangesFilterOperator` union documents exactly which are and are not supported); fixture ids are uuids, so no value needs the builder's quoting rules.

**KN-7. Match Centre's Stats tab draws a missing statistic as a real zero.** In `StatsTab` (`src/components/matches/match-centre-tabs.tsx`), `const homeNum = homeVal ?? 0` feeds the comparison bar while the numeric label correctly renders `-` for null. When one side has xG and the other does not — routine on API-Football's free tier, which is why `fixture_statistics.expected_goals` is nullable by design — the bar renders a confident 100%/0% split next to a literal "not reported" dash. That is a fabricated visual claim in the one section of the app most likely to be screenshotted. Fix: when either side is null, render the row without a bar. **Small.**

> **BUILT (2026-08-18).** When either side is null the row keeps its numbers (`-` for the missing one) and renders one flat neutral rail in place of the split — nothing to compare, so nothing is claimed. A `title` says why on hover. Worth stating plainly since this is the honesty rule rather than a layout preference: the bug was not that the bar looked odd, it was that the app drew a confident 100%/0% claim directly beneath the words that said the number was never reported.

**KN-8. `/live`'s own copy hardcodes a provider that may not be in use.** `src/app/(app)/live/page.tsx` renders "Matches in progress right now, synced from API-Football." `FOOTBALL_DATA_PROVIDER` selects between two real implementations. In a codebase whose first rule is not asserting things it hasn't verified, a hardcoded vendor name in user-facing copy is the same class of error as a fabricated stat. Fix: read the active provider name (`getActiveProviderStatus()` in `src/lib/football/index.ts` already returns it side-effect-free — the cron route uses it for exactly this reason). **Small.**

> **BUILT (2026-08-18).** Reads `getActiveProviderStatus().label` and passes it into the copy. When no provider is configured it returns null and the sentence simply doesn't name a source, rather than naming one KIVO isn't using.

### 1b. Performance and scale defects

**KN-9. Every match notification does one database round trip per recipient.** `insertNotifications` in `src/lib/football/match-notifications.ts` runs `ids.map(async (id) => shouldNotify(supabase, id, column))`, and `shouldNotify` (`src/lib/notification-preferences.ts`) is a single-row `notification_preferences` select. One goal for a club with N followers is N concurrent queries fired from inside a sync, before a single notification row is written. The file's own comment argues this matches its "simplicity over scale" trade-off, which was reasonable when it was written — it stops being reasonable the moment a popular club has real followers, and the fix is one line: a single `.in("profile_id", ids)` select, defaulting absent rows open exactly as `shouldNotify` already does. **Small.**

> **BUILT (2026-08-18).** `filterNotifiable` in `src/lib/notification-preferences.ts`, used by `insertNotifications`. Two things the one-liner as written would have missed: the ids travel in a URL-encoded PostgREST `in.(...)` filter, so an unbounded audience reintroduces KN-15's failure mode in a different file — it is chunked at 300 and the chunks run in parallel. And an unreadable chunk fails **closed** rather than open: an absent row means "hasn't set a preference" and is safe to default to notify, but a failed query means "we don't know", and not knowing is not consent. `shouldNotify` stays for the genuinely single-recipient producers (social, follows, comments).

**KN-10. `upsertSeason` is an unbatched three-queries-per-fixture N+1 that item 27's batching pass missed.** `RECOMMENDATIONS.md` item 27 batched competition, team and venue mapping lookups (`batchFindMappedIds`) and is marked RESOLVED. `upsertSeason` in the same file (`src/lib/football/sync.ts`) is still called once per fixture inside the loop, and each call issues a select plus two updates (`is_current = false` on siblings, `is_current = true` on this one) — even when the previous fixture in the same loop already resolved the identical `(competition_id, season)` pair. A 300-fixture day is roughly 900 avoidable round trips. Fix: memoize per `(competitionId, seasonYear)` for the run, the same in-place-mutated `Map` pattern the other three upserts already use. **Small.**

> **BUILT (2026-08-18).** `createSeasonResolver`, scoped to one run. Not the in-place-mutated `Map` pattern the item suggests, and deliberately: that pattern only works in a sequential loop, and the loop is now a bounded worker pool (KN-11) where several lanes reach the same unresolved key before any of them fills the map. The resolver memoizes the **promise** (`createAsyncMemo`) so concurrent callers share one round trip, and additionally serializes per competition (`createKeyedSerializer`) because `upsertSeason`'s two `is_current` writes are only safe against `idx_seasons_one_current_per_competition` while no other season of the same competition is being flipped concurrently — two different years are two different memo keys and the memo alone would interleave them.

**KN-11. The fixture loop in `syncTodayFixtures` is fully sequential, with notification fan-out inline.** The `for (const fixture of fixtures)` loop awaits every upsert in series, and `upsertFixture` awaits `notifyFixtureStatusChange` (which is itself KN-9) before moving on. On a serverless function with a wall-clock timeout, that is the shape most likely to be killed mid-run — leaving KN-4's stuck `running` row behind. Fix: bounded concurrency (a small worker pool) over the fixture list, and move notification fan-out out of the write path onto a queue or a post-run pass. **Medium.**

> **BUILT (2026-08-18).** Both halves. The loop is `mapWithConcurrency(fixtures, 6, …)` (`src/lib/concurrency.ts`, unit-tested: order preserved, limit never exceeded, rejection semantics) — six chosen against Supabase's per-project connection pool, which is the actual scarce resource here, not the provider: the whole day is fetched in one request before the loop starts, so no amount of concurrency in it spends extra quota. Each fixture's two team upserts and its venue upsert also now run together rather than in series. `upsertFixture` no longer fires notifications; it **returns** the status-change description, and the run dispatches them after the run row is already terminal, each contained per fixture. No queue was invented — there is no queue infrastructure in this codebase and pretending otherwise would have been the wrong kind of ambition; a post-run pass gets the whole benefit (football data can no longer be delayed or lost behind a notification fan-out) with nothing new to operate.

**KN-12. `sync-match-details.ts` still does per-row provider-mapping lookups everywhere.** `RECOMMENDATIONS.md` item 29 extracted `findMappedId`/`createMapping` into `src/lib/football/provider-mappings.ts` (de-duplication) but did not batch them, and item 27's batching never reached this file. Concretely: `processLineupSide` calls `findMappedId` once per player entry (~22 per side, ~44 per fixture); `processEvents` calls it up to three times per event (team, player, related player) plus one for the event's own mapping; `syncStandings` calls `upsertTeam` per row (20 rows × 2–3 queries). Fix: the same up-front batch resolve `syncTodayFixtures` already proved out. **Medium.**

> **BUILT (2026-08-18).** All three sites. `batchFindMappedIds` moved out of `sync.ts` into `provider-mappings.ts` — the module's own comment used to explain that folding a single-caller helper in would be a false consolidation, which was right then and stopped being right the moment this file became the second caller — and gained chunking at 100 ids on the way, since a broad fixtures day's ids ride in a URL-encoded GET filter. `syncFixtureDetails` resolves every team, player and event provider id the run will reference in three round trips after the fetches complete (by which point every id it will ever ask about is already known, which is what made the per-row lookups avoidable rather than merely unfortunate); `syncStandings` resolves the whole table's teams in one. Two details beyond the batching: `processLineupSide` re-checks only the players still unmapped after an auto squad sync, so a squad inserted mid-run is not missed, and its ~22 independent row upserts now run in a bounded pool with messages collected in input order so a concurrent pool cannot reorder the admin-facing failure list. `processEvents` is deliberately left sequential — each iteration can fire a notification and write a Match Room post, and the order those land in a live Room is the order the events happened.

**KN-13. The social feed transfers every comment row on the page in order to count them.** `fetchPostsPage` (`src/app/(app)/social/posts.ts`) runs `supabase.from("comments").select("post_id").in("post_id", postIds)` and then counts client-side. For a 20-post page that is fine; for one genuinely popular post it transfers thousands of rows to produce one integer. The reactions query above it has the same shape — `RECOMMENDATIONS.md` item 37 (still open) names the reactions half; the comments half is new, and arrived with item 7's comment UI. Fix: fold both counts into the `posts_with_counts` view item 37 already proposes, rather than solving reactions alone. **Medium.**

> **BUILT (2026-08-18).** `get_post_engagement(p_post_ids uuid[])` (migration `0060`) returns both counts per post, and `fetchPostsPage` now fetches only the **viewer's own** reaction rows — bounded by the page size no matter how popular anything on it is — instead of every reaction row on the page. An RPC rather than item 37's view, because a view cannot take the page's post ids as a parameter and would have to be filtered after the fact. The load-bearing decision is that it is **SECURITY INVOKER**, unlike every other aggregate in this schema: `comments_select_public` and `reactions_select_public` are public selects that migration `0045` narrowed to hide shadow-muted authors, and a `security definer` function would have quietly counted those rows back into everyone's feed — silently undoing a moderation control while looking like a performance change. Running as invoker means these are exactly the counts the caller could have computed themselves.

**KN-14. Poll results are fetched one RPC call per poll on every feed page.** Same file: `pollPostIds.map(async (postId) => supabase.rpc("get_poll_results", { p_post_id: postId }))`. The code comment argues polls will be a small minority of any page, which holds for `/social` and does not hold for a Match Room during a live match (the exact place `RECOMMENDATIONS.md` item 306 wants polls to live). Fix: `get_poll_results(p_post_ids uuid[])`, matching `get_prediction_consensus`'s existing array-parameter shape. **Small.**

> **BUILT (2026-08-18).** One RPC per page (`get_poll_results_for_posts`, migrations `0060` + `0063`). Named rather than overloaded, and the reason is worth recording because the obvious version does not work: adding `get_poll_results(uuid[])` alongside the existing `get_poll_results(uuid)` makes Supabase's type generator emit a **union** of `{ Args, Returns }` shapes, and supabase-js's `.rpc()` collapses that union when resolving the argument type, so passing a `uuid[]` is rejected against the scalar overload's `Args`. `0060` applied it as an overload, `0063` renames it — both are in the repo because both really happened to the database. The scalar function is deliberately left in place: a concurrent session's `0059` revokes a grant on it by name, and dropping it would break a from-scratch replay of this migration history. The failure/empty distinction `docs/BUG_AUDIT_2026-08-18.md` S5 protects is preserved: one failed call means every poll on the page reports results-unavailable, which is the honest read of what happened.

**KN-15. `/home`'s followed-team filters are built as a string that grows with the follow count.** `src/app/(app)/home/page.tsx` builds `.or(matchdayTeamIds.map((id) => \`home_team_id.eq.${id},away_team_id.eq.${id}\`).join(","))`. Each followed team adds ~86 characters to a URL-encoded GET query string. A user following 100 teams produces a filter well past what proxies and PostgREST will accept, and it fails as an opaque request error rather than a graceful degradation. Fix: two `.in()` filters OR'd once, or a small RPC. **Small.**

> **BUILT (2026-08-18).** `fetchFixturesForTeams` (`src/lib/football/fixtures-by-team.ts`, unit-tested). Neither of the two options as written, and for a reason worth recording: both are still **linear** in the follow count, so both only move the cliff rather than removing it, and the RPC would have cost a migration on a branch four agents are sharing. The ids are chunked at 30 instead, which makes the per-request length a constant this code picks rather than something a user's behaviour decides, and each chunk is asked for with two plain `.in()` queries (home side, away side) rather than any `.or()` grammar at all — half the URL length and nothing that can be subtly mis-parsed. Chunks run in parallel, so a heavy follower costs concurrency, not latency. Merging each sub-query's sorted prefix is exact, not approximate: the earliest N of the union is necessarily inside the union of the earliest-N prefixes. This also failed in the worst possible direction before — hardest for the most engaged users, and silently, since the whole "your teams" section just disappears on a rejected request.

**KN-16. Neither of `/home`'s followed-team fixture queries nor `/live`'s live-fixture query has a `LIMIT`.** `matchdayFixtures` (`home/page.tsx`), `liveFixtures` and `todayFixtures` (`live/page.tsx`). Every other list surface in the app is bounded (`RECOMMENDATIONS.md` items 111–113 established the convention). **Small.**

> **BUILT (2026-08-18).** All three, plus the one the item doesn't name (`/home`'s `upcomingFixtures` already had `.limit(6)`, now a named constant beside the others). `/live` gets separate ceilings for live and today's fixtures so a busy day of scheduled matches can never crowd an in-progress one out of the list, and those ceilings also bound what the Realtime subscription downstream has to watch (KN-6).

**KN-17. `/home` issues three sequential round trips after its `Promise.all`.** `followedTeamRows` must resolve first (it feeds the other two), but `matchdayFixtures` and `yourTeamsFixtures` are independent of each other and are still awaited in series. Fix: `Promise.all` the second pair. **Small.**

> **ALREADY FIXED — no change needed (verified 2026-08-18).** `matchdayFixtures` and `upcomingFixtures` (the item calls the latter `yourTeamsFixtures`) are already awaited together in one `Promise.all` in `src/app/(app)/home/page.tsx`; the page was restructured around its lead slot after this document was written. Recorded rather than silently skipped, since "it's already done" is a real outcome and re-doing it would have been churn. Both queries in that pair were changed for KN-15/KN-16, but their concurrency was not the reason.

**KN-18. `buildGroundingContext` re-runs the entire retrieval on every single chat turn.** `src/lib/ai/grounding.ts` fires: one `follows` query, three entity-resolution queries, one fixtures query, `computeTeamForm` for up to four followed teams, `computePlayerForm` for up to four followed players, and `buildMatchInsights` when focused. That is 15–25 queries per user message, on an endpoint already rate-limited *because it is expensive*. Nothing in it changes between two messages sent thirty seconds apart. Fix: cache the built summary per `(profileId, focus)` for a short TTL, or per conversation turn. **Small–Medium.**

## 4. Backend, data and schema

**KN-81. BUILT (2026-08-18). The sync pipeline has no concept of a partial or failed *entity*, only a failed run.** `sync_runs` records `records_processed` and a truncated `error_message` (capped at 20 concatenated failures). When fixture 47 of 300 fails, nothing records *which* fixture, so nothing can retry it and Data Health cannot show a per-entity failure list. A small `sync_run_failures` table (`sync_run_id`, `entity_type`, `provider_entity_id`, `error`) makes retries targeted instead of "run the whole day again". **Medium.** — *Built in migration `0056`, plus a `resolved_at` column the item did not ask for and which is what turns the log into a work queue: a failure closes only when a later run genuinely succeeds on that same provider entity (`resolve_sync_run_failures`, one bulk statement per run — never on a timer, never because the run "looked fine"). Wired into `syncTodayFixtures` and `syncStandings`; surfaced as "Unresolved entity failures" on Data Health.*

**KN-82. BUILT (2026-08-18). Sync is fire-and-forget with no idempotency key, so two overlapping runs do the same work twice.** The cron route dedups against a `running` row for two minutes (`DEDUP_WINDOW_MINUTES`), which is a heuristic, not a lock — and KN-4 shows it can be poisoned by a stuck row. A Postgres advisory lock keyed on `(provider, entity_type)` held for the duration of a run is the standard, cheap, correct version. **Small.** — *Built in migration `0056`, but deliberately **not** as a session advisory lock, and the difference matters: a session lock lives on one Postgres connection, and every call this app makes goes through PostgREST's per-request pooled connections, so a lock taken inside an RPC is released the instant that RPC returns — it could never span the dozens of round trips a run makes. What was built is a lease (`sync_locks` + `claim_sync_lock`/`renew_sync_lock`/`release_sync_lock`), which is the standard answer when a lock must outlive a connection; an advisory lock still serialises the claim itself. Two things this gets that the proposal would not have: an expired lease is reclaimable, so a crashed worker cannot wedge the pipeline the way KN-4's stuck row did, and the lease is keyed on the work rather than the trigger, so an admin "Sync now" and the cron worker now exclude each other (the old heuristic only ever looked at cron rows). The cron route's two-minute heuristic is replaced by reading the lease. Claim/renew/release/takeover semantics verified live with real SQL.*

**KN-83. `provider_mappings` has no notion of a provider switch, which is the abstraction's whole point.** `FootballDataProvider` exists so KIVO can change vendors. `provider_mappings` keys on `(provider, entity_type, provider_entity_id)`, so switching providers creates a **second, disconnected universe** of teams and fixtures — the same real club existing twice with no link. `docs/PROVIDER_ABSTRACTION.md` and `RECOMMENDATIONS.md` item 298 both acknowledge that reconciling two providers' ids is a genuinely separate feature. The cheap first step is not failover: it is an admin **entity-merge** tool (pick two rows that are the same real club, repoint every FK, keep both mappings), which is also exactly what `RECOMMENDATIONS.md` item 255's duplicate-detection panel would feed. Build the merge before the detection. **Large.**

**KN-86. BUILT (2026-08-18). Nothing ever deletes or archives a fixture the provider stops reporting.** `upsert_fixture_with_mapping` only ever writes. **KN-87. BUILT (2026-08-18). `fixture_events` has no unique constraint on the real-world event, only on the provider mapping.** Dedup relies entirely on `provider_mappings` (`findMappedId` on the event's provider id). > **BUILT (2026-08-18).** Ratio closed and, more importantly, made unable to reopen: 122 `console.error` call sites converted across 41 files, and `eslint-rules/no-bare-console-error.mjs` fails the build on the next one. The mechanical half was done mechanically, but not blindly — the codemod derives a real, greppable context tag from the module path plus the message (`football.sync.startRun`, `admin.users.suspendUser`), because a uniform placeholder would have made the structured sink no more searchable than `console` was, which is the whole point of having one. Two things worth knowing. Interpolated messages carried per-call detail the static tag cannot hold (a fixture id, a provider name) and now move to `logError`'s metadata rather than being dropped — otherwise the structured log would have been strictly *less* useful than the console line it replaced. And the rule is deliberately **not** auto-fixable: the fix needs a tag chosen by someone who knows what the call site does, and a rule that invented one would fill the logs with tags nobody can search for. `src/lib/log.ts` is exempt because it is the sink; tests are exempt because a test asserting on console output is testing the sink, not bypassing it.

**KN-130. Zero tests cover any server action.** 16 test files against ~300 source files, and `docs/STRUCTURAL_SURVEY.md`'s own count is 31 files carrying `"use server"` with no coverage of any of them. The specific gap that matters is authorization: `submitPrediction`'s kickoff lock, `setGameweekRoster`'s deadline lock, `reportContent`'s ownership, `signOutOtherDevices`'s scoping, `sendEmailCode`/`verifyEmailCode`'s input handling, and every admin action's role gate. These are pure-ish functions behind a Supabase client and are testable with a mocked client. **Medium.**

**KN-131. Cross-user RLS isolation is now covered by nothing, and CI would not have run the coverage even when it worked.** `src/lib/supabase/rls-anon.integration.test.ts` covers the anon case only and explicitly defers cross-user isolation to `scripts/verify-rls.sql` — which `RECOMMENDATIONS.md` item 323 has just established no longer exercises anything after migration `0053` dropped `private.current_clerk_user_id()`. Item 323 owns the harness rewrite and scopes it well. The part it does not cover, and this item does: **even when the script worked, nothing ran it.** `.github/workflows/ci.yml` runs `tsc`/`eslint`/`build`; a `.sql` file a human remembers to paste into the SQL editor is not regression coverage. Whatever item 323's rewritten harness ends up being, it needs a CI step against a Supabase branch database, or it will silently rot again the next time identity changes. **Medium.**

**KN-132. Nothing tests that a migration applies cleanly from zero.** 53 migrations, applied incrementally to one live project. There is no CI step that runs them in order against an empty database, so a migration that only works because of the live project's current state would not be caught until it mattered. **Small.**

**KN-133. CI runs `tsc`, `eslint` and `build`, but not `vitest`.** Worth verifying against `.github/workflows/ci.yml` (currently being edited by a sibling session) — the 16 test files that exist are only a quality gate if they run. **Small.**

**KN-134. There is no bundle-size or performance budget.** `@vercel/analytics` is wired (item 212) and reports real user timing; nothing fails a build when the shell grows. For a product whose stated market is mobile-network-constrained, a size budget on the app-shell chunk is the one guardrail that stops a slow, invisible slide. **Small.**

**KN-135. `/api/health` exists and nothing calls it.** `src/app/api/health/route.ts` (item 214). No uptime monitor is configured or documented. Whichever external scheduler ends up driving KN-99 can almost certainly also ping this. **Small.**

**KN-136. There is no staging environment and no documented way to make one.** Every change is verified by `tsc`/`eslint`/`build`/`test` and then goes to the one live Supabase project. Supabase branching exists; nothing in `ENVIRONMENT.md` or `docs/` describes using it. That is fine with five users and unacceptable the first time a migration is wrong. **Medium.**

**KN-137. `ICON_MANIFEST.md` documents 155 icons as a deliberate design library (item 88's chosen resolution) and nothing enforces the mapping.** A renamed or deleted asset breaks a page at runtime with no build-time signal. A tiny script comparing the manifest to `public/assets/` in CI closes it. **Small.**

**KN-138. The repo root has 16 multi-megabyte PNG screenshots committed at top level.** `051BBEDD-…png` through `F1296979-…png` — roughly 37MB. They are not referenced by anything in `src/`. Whatever they are for, the repo root is not it: move them to a `design/` subfolder or out of git, and note in `.gitignore` how future ones should be handled. **Small.**

## 8. Explicitly not buildable

Named so they stop being re-proposed, each with the specific verified reason. This section extends `RECOMMENDATIONS.md`'s own "Explicitly not buildable" list (items 178–181) and section 18's out-of-scope note rather than repeating them.

**KN-139. Per-90-minute statistics, minutes-played leaderboards, or any rate stat with a time denominator. NOT BUILDABLE.** `lineups` (migration `0001`) has `is_starting`, `shirt_number`, `position` and `formation` — no minutes column anywhere, confirmed against every migration. `docs/RATING_ENGINE.md` and the rating engine's own doc comment say the same. Any per-90 figure would divide by an invented denominator.

**KN-140. A live "which of your fantasy players just scored" ticker, or any per-player fantasy points display. NOT BUILDABLE.** `fantasy-scoring.ts` computes `scoreRosterSlot` per player in memory, and only the team-level sum is persisted to `fantasy_points` (keyed `(fantasy_team_id, gameweek_id)`). There is no per-player-per-gameweek row to read back. `RECOMMENDATIONS.md` items 296 and section 18 reach this same conclusion independently.

**KN-141. Percentile ranks, "top 10% of KIVO managers", or any cohort-relative stat. NOT BUILDABLE today.** There is no cohort. The live project has a handful of profiles and, per item 225, zero finished fixtures. Every existing aggregate in this codebase that could mislead is already suppressed below a minimum sample (`MIN_MEANINGFUL_SAMPLE = 3` in `PredictionCard`, `FanRatingCard`, `/predictions/mine`) — a percentile is that problem with no honest floor.

**KN-142. "Trending", "hot right now", view counts, or anything time-windowed over attention. NOT BUILDABLE.** There is no view-tracking table and no analytics event log (`RECOMMENDATIONS.md` item 212). `src/components/ui/track-view.tsx` and `src/lib/recently-viewed.ts` are client-local only. `get_most_followed_teams` is deliberately labelled "Popular", not "Trending", for exactly this reason — and that precedent should hold.

**KN-143. Any match outcome forecast, win probability, expected points, or "form suggests". NOT BUILDABLE BY POLICY.** Not a data limitation — a deliberate product position (`RECOMMENDATIONS.md` items 178 and 246, `DECISIONS.md`'s no-gambling entry). KIVO explains what happened and what is verifiably true; it does not predict results. Fan **polls** about outcomes are fine (they are labelled opinion); a KIVO-computed number is not.

**KN-144. Injuries, suspensions, referee assignments, and xG on most competitions. NOT BUILDABLE on the current tier.** Confirmed in `BUILD_STATUS.md` against API-Football's free tier. `fixture_statistics.expected_goals` is nullable precisely for this — see KN-7 for the bug where a null xG currently renders as a real zero anyway.

**KN-145. Positional heatmaps, player movement, pass maps, or anything on pitch coordinates. NOT BUILDABLE.** `HeatmapEngine` and `HeatmapView` are built and tested; no `PositionalDataProvider` is implemented by any provider, so the observation set is always empty. The honest empty state on the Heatmap tab is correct behaviour, not a gap to fill.

**KN-146. Squad age profiles, nationality breakdowns, and contract data. NOT BUILDABLE.** `getSquad`'s own comment records that the free tier returns neither date of birth nor nationality (TheSportsDB does supply real DOB, which is why item 30's note exists — but the default provider does not, so a cross-competition age chart would be inconsistently sourced). `market_value_eur`/`contract_expires_at` were deliberately dropped by migration `0039`.

**KN-147. Real-time push notifications to a closed app. NOT BUILDABLE.** No push infrastructure, no service worker, no `manifest` push config, and `notification_deliveries` still has no producer (item 11). Everything the notification system does today is in-app only, and `shouldNotify` correctly treats `in_app_enabled` as an unconditional floor for that reason.

**KN-148. Live commentary text beyond what `fixture_events` contains. NOT BUILDABLE.** `RECOMMENDATIONS.md` item 248 correctly scopes a deterministic commentary strip to real stored events. Anything richer — narrative build-up play, possession chains, "dangerous attack" — has no source. Writing it with an LLM would be fabrication with a friendly voice.

## 9. If you only do ten things

Ordered by leverage: things that are currently broken outrank things that are currently missing.

1. **KN-1 and KN-2** — crests and player photos are blocked by KIVO's own CSP, and switching providers breaks Match Centre. Two config lines and one component swap. Nothing else on this list matters if the app renders without club badges.
2. **KN-116, KN-117 and KN-118** — unthrottled OTP, unverified email deliverability, and no recovery path when a code doesn't arrive. With email OTP as the only door, these three are the door.
3. **KN-119 and KN-124** — decide, in `DECISIONS.md`, what gating means for 11,000 sitemap URLs and for the four real users whose accounts are about to become unreachable. Both get harder every day they're deferred.
4. **KN-4, KN-9 and KN-10** — the sync path's three real defects: a run that can hang forever and block the worker, a notification fan-out that is one query per follower, and a season upsert that item 27's batching missed.
5. **KN-99** — pick the scheduler. The live worker is built, tested and currently attached to nothing; `docs/STRUCTURAL_SURVEY.md` calls this the single biggest lever in the product, and it is now a one-line caller decision.
6. **KN-36, KN-37 and KN-40** — the first screen a new user sees currently explains KIVO's admin tooling to them. Fix the copy, give `/home` a priority order, and use onboarding's one guaranteed moment of attention to make `/home` non-empty.
7. **KN-27 and KN-120** — stop `anon` grants regenerating by default, then audit the ones that exist against a product that no longer has guests.
8. **KN-7 and KN-21** — the two honesty defects: a missing statistic drawn as a real zero, and a notification system that can put thirty rows in one bell from one user.
9. **KN-31 and KN-3** — two places where the product promises something the pipeline cannot deliver: a date strip over days that can never have data, and a `BUILD_STATUS.md` row claiming a cron that no longer runs.
10. **KN-130 and KN-131** — 31 files of server-action authorization logic tested by nothing, and an RLS harness that migration 0053 silently broke (`RECOMMENDATIONS.md` item 323) and that CI never ran anyway. This is the item that stays invisible right up until it isn't.
