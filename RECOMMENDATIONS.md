# KIVO Recommendations

Generated 2026-08-14 from a full read of the codebase: every root-level `.md`, all ten files under `supabase/migrations/`, and every file under `src/` (all 22 routes under `src/app/(app)/`, the `/admin` tree, all 26 components, the football provider abstraction in `src/lib/football/`, the AI grounding layer in `src/lib/ai/`, `globals.css`, and the Next/ESLint/TS config). No live browser was used, so every UI finding is reasoned from the JSX and Tailwind classes directly.

This document supersedes the earlier competitive-research log that lived at this path (preserved in git at commit `e515a6d`). That log was outside-in market research; this one is inside-out codebase audit. Still-open items from it are folded in and marked where relevant.

Every recommendation here respects the platform's standing rules: zero fabricated football data, $0 provider budget with no cron or polling, Clerk as sole identity authority, RLS-gated Supabase for application data only, and guest-viewable surfaces with sign-up-gated actions. Where an idea brushes against the fabrication line, the honesty constraint is stated explicitly. A handful of ideas are listed specifically as **not buildable** so they stop getting re-proposed.

**2026-08-18 update — "no cron or polling" is no longer a standing rule.** The founder explicitly directed the opposite: a real, adaptive Vercel Cron worker (`src/app/api/cron/sync-live/route.ts`, every minute, no-ops unless a fixture is actually live or imminent) is now built specifically to be the industry-standard replacement for the admin-clicked-button pattern this line describes. `FOOTBALL_LIVE_POLLING_ENABLED` — the "$0 budget" safety valve — is unaffected and stays the real gate (see `src/lib/football/index.ts` and `docs/LIVE_DATA.md`); what changed is that a schedule now exists to respect that gate automatically instead of a human being the only thing that ever calls `syncTodayFixtures`. Left the original sentence above as the historical record of the constraint this pass superseded, per this document's own convention of annotating rather than rewriting past entries.

Sizes: **Small** (under a day), **Medium** (a few days), **Large** (a week or more, or needs a schema plus UI plus pipeline change).

## 1. Blocking gaps: features that are built but cannot currently work

These are the highest-leverage findings in the document. Each one is a surface that renders, compiles, and looks finished, but can never leave its empty state because nothing in the codebase writes the data it reads.

1. **Nothing ever sets `seasons.is_current = true`.** `upsertSeason()` in `src/lib/football/sync.ts` inserts with the column's `false` default and never revisits it. Consequences cascade: `/fantasy` filters `seasons.eq("is_current", true)` so league creation permanently shows "No active season yet"; `/teams/[id]` picks `standingsRows.find(s => s.season?.is_current)` so "League position" is permanently empty even after a standings sync. Fix in the sync: mark the newest season per competition current (the unique partial index `idx_seasons_one_current_per_competition` already enforces one per competition). **Small.** **RESOLVED (2026-08-18):** `syncTodayFixtures` now marks the newest season per competition `is_current = true` and unsets any prior current season (`src/lib/football/sync.ts` lines ~161-171).

2. **`fantasy_gameweeks` is never inserted anywhere.** Grep confirms only reads (`fantasy/page.tsx`, `fantasy/actions.ts`). Without a gameweek row the squad builder shows "No gameweek is open yet for this season" forever, which means the entire 844-line `fantasy-builder.tsx` is unreachable. Add an admin action that derives gameweeks from real synced fixtures (group a season's fixtures into rounds by `matchday`, or by week when `matchday` is null, deadline = first kickoff of the round). This is derived from real fixture data, not invented. **Medium.** **RESOLVED (2026-08-18):** `admin/data-health/fantasy-actions.ts` derives and inserts `fantasy_gameweeks` from synced fixtures.

3. **Predictions are never scored.** `predictions.points_awarded` and `locked_at` are read but never written. `/predictions` correctly refuses to fabricate anything, so the leaderboard is permanently the empty state. Add an admin-triggered scoring pass (same on-demand pattern as the syncs, never cron) that runs over fixtures with `status = 'finished'`, compares `predicted_outcome` to the real result, writes `points_awarded` and `locked_at`, and awards XP via the existing `awardXp` helper. **Medium.** **RESOLVED (2026-08-18):** admin-triggered scoring in `admin/data-health/predictions-actions.ts` writes `points_awarded`/`locked_at` and awards XP.

4. **The predictions leaderboard query is dead by RLS even after scoring lands.** `predictions_select_own` restricts every caller to their own rows, so the cross-user aggregate in `predictions/page.tsx` can only ever see the viewer. This needs a `SECURITY DEFINER` RPC returning `(profile_id, username, total_points)` only, in the same shape as `get_fantasy_league_leaderboard`. Without it, item 3 produces a leaderboard of one. **Small** (migration only). **RESOLVED (2026-08-18):** migration `0012_predictions_leaderboard.sql` adds a `SECURITY DEFINER` `get_prediction_leaderboard` RPC, read by `predictions/page.tsx`.

5. **`fantasy_points` is never written.** Same shape as item 3: the fantasy leaderboard's honest "No gameweeks scored yet" state is permanent. Once gameweeks (item 2) and finished fixtures exist, add an admin-triggered scoring pass over `fantasy_rosters` joined to `fixture_events`, writing `fantasy_points`. Publish the scoring rules in the UI so points are auditable. **Large.** **RESOLVED (2026-08-18):** `fantasy_points` is written by the same admin-triggered pass in `admin/data-health/fantasy-actions.ts`, with scoring rules documented in the UI.

6. **There is no way for a user to file a report.** `reports` is read in three admin files and written in none. The whole moderation queue, the SLA-aware urgency badges, and `moderation_actions` audit trail can never receive a single item. Add a report affordance on `PostCard` (and later comments/profiles) writing to `reports` under the existing `reports_insert_own` policy. **Small.** **RESOLVED (2026-08-18):** `social/report-actions.ts` inserts into `reports` from a report affordance wired up on posts, under `reports_insert_own`.

7. **The `comments` table has zero UI.** Full schema, RLS, threading support via `parent_comment_id`, and indexes exist. Not one line of `src/` references it. Ship comment threads on posts. **Medium.** **RESOLVED (2026-08-18):** `src/components/social/comment-thread.tsx` ships full threaded comment UI (create/reply/react) against the `comments` table.

8. **Match Rooms do not exist.** `posts.fixture_id` exists with an index and the comment "set => match-room post"; the landing page markets "Match Rooms, alive... React to goals in real time, not a comment section bolted on." Nothing in `src/` ever sets or filters on `fixture_id`. Add a Room tab to `MatchCentreTabs` that reads and writes fixture-scoped posts. This is the single biggest gap between what the product claims and what it does. **Medium.** **RESOLVED (2026-08-18):** `src/components/matches/match-room.tsx` reads and writes fixture-scoped posts via `posts.fixture_id`, wired into `MatchCentreTabs`.

9. **`fixture_statistics` (migration 0005) is completely dead.** Seventeen real per-team stat columns, RLS policies, an index, and a careful comment about not modelling Sofascore-proprietary metrics. There is no `getFixtureStatistics` on the `FootballDataProvider` interface, no sync, and no UI. Add the provider method against `/fixtures/statistics?fixture=`, wire it into `syncFixtureDetails`, and add a Stats tab to Match Centre. **Medium.** **RESOLVED (2026-08-18):** `getFixtureStatistics` exists on `FootballDataProvider`, is synced in `sync-match-details.ts`, and rendered on Match Centre.

10. **`notification_preferences` is never read or written.** Eight boolean toggles the settings page doesn't expose. Either ship the preferences UI (item 133) or the table is decoration. **Small.** **RESOLVED (2026-08-18):** `settings/actions.ts` reads/writes `notification_preferences`; `src/components/settings/notification-preferences-panel.tsx` exposes all eight toggles.

11. **`notification_deliveries` has no producer.** There is no delivery pipeline of any kind. Keep it, but mark it explicitly as reserved in `ARCHITECTURE.md` so it does not read as shipped. **Small.**

12. **`profiles.favourite_team_id` can never be set through the product.** It is read once, in `src/lib/ai/grounding.ts`, and written nowhere. This is the anchor for the entire personalization story. Add a team picker (see item 128). **Small.** **RESOLVED (2026-08-18):** `onboarding/actions.ts` sets `favourite_team_id` via a team picker step; `home/page.tsx` uses it for the "Your teams"/matchday module.

13. **`follows` rows are write-only from the user's perspective.** Users can follow teams, players and competitions from three detail pages, but nothing in the app reads follows to change what a user sees. No "your teams" module, no followed-entity feed filter, no following list page. The star button currently does nothing observable. **Medium.** **RESOLVED (2026-08-18):** `home/page.tsx` now builds a real "Your teams" module from `follows` plus `favourite_team_id` (item 174 shipped alongside this).

14. **Five of six `reaction_type` enum values are unreachable.** Only `like` is used in `social/actions.ts`. `fire`, `clap`, `laugh`, `wow`, `sad` exist in the DB and would meaningfully raise expressiveness during a match. **Small.** **RESOLVED (2026-08-18):** all six values are live in `src/components/social/reaction-picker.tsx`.

15. **`audit_log` is never written.** Moderation writes `moderation_actions`; nothing writes the general-purpose audit table, so admin role changes, data syncs, and user deletions leave no trail. Wire the admin server actions to it or drop the table. **Small.** **RESOLVED (2026-08-18):** `src/lib/audit.ts`'s `logAudit` is wired into admin server actions (role changes, syncs, reconciliation, moderation).

16. **`profiles.bio`, `profiles.country` and `profiles.avatar_url` have no editor.** `avatar_url` is synced from Clerk by the webhook and then never rendered anywhere (every avatar in the app is a gradient initial). **Small.** **RESOLVED (2026-08-18):** `settings/actions.ts` and `profile/page.tsx` expose editors for `bio`, `country`; avatar has a full `AvatarPicker` (kivo-id/uploaded/Clerk-synced) rendered via `resolveAvatarSrc`.

17. **Fantasy rosters do not carry forward between gameweeks.** `fantasy_rosters` is keyed on `(fantasy_team_id, gameweek_id, player_id)` and `fantasy/page.tsx` loads only the current gameweek. When GW2 opens, the user's squad appears empty and must be rebuilt from scratch. Copy the previous gameweek's roster forward on first load of a new gameweek. **Medium.** **RESOLVED (2026-08-18), correcting item 240's spot-check:** the per-viewer half of this was already shipped in commit `1fb8d13` (2026-08-14/15, `src/lib/fantasy.ts`'s `carryForwardFantasyRoster`, called from `fantasy/page.tsx` on first load of a gameweek with no roster rows yet) — item 240's earlier spot-check grepped only `fantasy/actions.ts` and missed it, since the logic lives in `lib/fantasy.ts`. Verified genuinely working: it walks back to the most recent prior gameweek this team actually built a squad for (skipping any gameweek they missed entirely), copies starting XI/bench/captain/vice-captain forward via an idempotent upsert, shows a "Carried forward from GW{N}" badge, and leaves the existing deadline lock (`setGameweekRoster` in `fantasy/actions.ts`) fully in control of when it can be edited — no separate lock logic invented. What genuinely was missing, and is now built in this pass: `scoreFantasyGameweek` (`admin/data-health/fantasy-actions.ts`) read `fantasy_rosters` directly with no fallback, so a team whose owner hadn't opened `/fantasy` since the gameweek went current still had zero roster rows at scoring time and would score nothing despite intending to keep their squad. Added `carryForwardMissingFantasyRosters` (`src/lib/fantasy.ts`) — a batched, service-role bulk version of the same walk-back logic covering every team in the gameweek's season — called at the top of `scoreFantasyGameweek` before rosters are read. No transfer mechanic invented; carry-forward only ever copies whatever the team's last real roster was. `tsc`/`eslint`/`build`/`test` all verified clean after this change.

18. **AI conversations are persisted but unreachable.** `ai_conversations` and `ai_messages` accumulate rows with titles derived from the first message, and there is no history list, no resume, no rename, no delete. Refreshing `/ai` starts over. **Medium.** **RESOLVED (2026-08-18):** `ai/actions.ts` has `loadConversationMessages`, `renameConversation`, `deleteConversation`; `ai/page.tsx` has a history list with resume/rename/delete.

19. **AI conversation history loads the wrong twenty messages.** `src/app/api/ai/chat/route.ts` does `.order("created_at", { ascending: true }).limit(MAX_HISTORY_MESSAGES)`, which returns the *oldest* twenty messages. Past message twenty, the model stops seeing anything recent. Order descending, take twenty, then reverse. **Small, and a real bug.** **RESOLVED (2026-08-18):** `api/ai/chat/route.ts` now orders `created_at` descending, limits, then reverses to chronological order before building the prompt.

20. **Guests see no author names on the social feed.** `posts_select_public` grants `anon` read on posts, but `profiles` has no `anon` SELECT policy at all, so the embedded `author:profiles(...)` join returns null for signed-out visitors and every post renders as "KIVO fan". Same problem on the predictions leaderboard join. Fix with a narrow public view or an `anon` policy exposing only `username`, `display_name`, `avatar_url`. **Small, and a real bug on the platform's most public surface.** **RESOLVED (2026-08-18):** migration `0011_public_profiles_function.sql`'s `get_public_profiles`/`get_public_profile_by_username` RPCs are granted to `anon` and used by the social feed and predictions leaderboard author joins.

--- **RESOLVED (2026-08-18):** migration `0011_public_profiles_function.sql`'s `get_public_profiles`/`get_public_profile_by_username` RPCs are granted to `anon` and used by the social feed and predictions leaderboard author joins.

## 2. Backend, schema and data model

21. **Add a `public_profiles` view (or narrow `anon` SELECT policy) and route every public-facing author join through it.** Fixes item 20 without loosening `profiles_select_own_or_admin`. Expose `id`, `username`, `display_name`, `avatar_url` and nothing else. **Small.** **RESOLVED (2026-08-18):** migration `0011_public_profiles_function.sql` ships `get_public_profiles`, exposing exactly `id`/`username`/`display_name`/`avatar_url` to `anon`.

22. **Sync writes are not transactional.** In `sync.ts`, a `fixtures` insert can succeed and its subsequent `provider_mappings` insert can fail, leaving an orphan fixture that the next sync will duplicate because `findMappedId` returns null. Wrap each entity's insert-plus-mapping in a `SECURITY DEFINER` RPC so both land or neither does. **Medium.** **RESOLVED (2026-08-18):** `upsert_competition_with_mapping`/`upsert_team_with_mapping`/`upsert_venue_with_mapping`/`upsert_fixture_with_mapping` RPCs (see calls in `src/lib/football/sync.ts`) make each entity-plus-mapping insert atomic.

23. **`upsertCompetition`, `upsertTeam` and `upsertVenue` never update.** They return early on an existing mapping, so a renamed club or a new crest URL is ignored forever. Update the row on every sync, using the same "never clobber with null" rule `sync-squads.ts` already applies to players. **Small.** **RESOLVED (2026-08-18):** `upsertCompetition`/`upsertTeam`/`upsertVenue` in `src/lib/football/sync.ts` now `.update()` the row on every sync for an existing mapping (name, short_name, crest_url), following the "never clobber with null" rule.

24. **`upsertVenue` writes `"Unknown venue"` placeholder rows** when the provider gives an id but no name. That is a fabricated string in a public table. Leave `venues.name` nullable, or skip creating the venue entirely. **Small.** **RESOLVED (2026-08-18):** `upsertVenue` no longer writes a placeholder string — a provider id with no reported name stays `null` (migration `0017_venue_nullable_name_and_enum_fixes.sql` made `venues.name` nullable).

25. **`toDbFixtureStatus` maps `"unknown"` to `"postponed"`.** That asserts a factual match state the provider never reported. Add `unknown` to the `fixture_status` enum, or leave the fixture at its previous status and log the unmapped code. **Small.** **RESOLVED (2026-08-18):** migration `0017_venue_nullable_name_and_enum_fixes.sql` adds `unknown` to the `fixture_status` enum; `toDbFixtureStatus` passes it through honestly instead of mapping to `postponed`.

26. **`sync_runs.entity_type` is misused for two run types.** Lineups plus events runs are recorded as `fixture_event`, and standings runs as `season`, both with apologetic code comments. The Data Health screen therefore mislabels its own history. Add `lineup` and `standing` to the `provider_entity_type` enum. **Small.** **RESOLVED (2026-08-18):** migration `0017_venue_nullable_name_and_enum_fixes.sql` adds `lineup` and `standing` to `provider_entity_type`, used by those sync runs.

27. **The sync loop makes roughly six sequential round trips per fixture** (competition lookup, season select, two team lookups, venue, fixture upsert, plus mapping inserts). An unfiltered `/fixtures?date=` day returns hundreds of fixtures worldwide, so one "Sync now" click is easily 1500+ sequential Supabase calls in a single server action. Expect timeouts. Batch the lookups (one `in()` query for all provider ids up front), then bulk upsert. **Medium.** **RESOLVED (2026-08-18):** `batchFindMappedIds` in `src/lib/football/sync.ts` does one `.in()` lookup per entity type up front for the whole day's batch, threaded through the upsert helpers instead of a per-fixture round trip.

28. **Scope `getFixturesByDate` to specific competitions.** Carried forward from the prior log and still open. API-Football supports `league=`, and the free tier's real constraint is request count, not response size, so scoping costs nothing and stops KIVO's `teams`/`competitions`/`venues` tables filling with leagues the product does not cover. **Small.** **Status: DONE (2026-08-15).** Config-driven via `FOOTBALL_SYNC_COMPETITION_IDS` (new, see `ENVIRONMENT.md`) — `src/lib/football/competitions-config.ts`'s `getSyncedCompetitionProviderIds()`, applied in `syncTodayFixtures` by filtering the already-fetched day's response (not one provider request per league — costs zero extra quota either way, per this item's own reasoning) before any competition/team/venue/fixture is written. Deliberately filters the response rather than calling `league=` per configured id: a single admin-triggered sync still costs exactly one provider request regardless of how many competitions are configured. Unset (the default) means no filter — this codebase has no existing "which leagues does KIVO cover" product decision recorded anywhere to hardcode as a default, so defaulting to a filtered set would be an invented assumption, not a real one; the admin-triggered sync flow is unchanged until an operator actually sets the var.

29. **The four sync files each redefine `findMappedId`, `createMapping`, `findProviderEntityId` and `upsertTeam`.** The duplication is documented as deliberate under an earlier file-scope constraint that no longer applies. Extract to `src/lib/football/provider-mappings.ts`. Four copies of the dedupe logic is four places for drift. **Small.** **RESOLVED (2026-08-18):** `src/lib/football/provider-mappings.ts` now holds the shared `findMappedId`/`createMapping`/`findProviderEntityId` logic.

30. **Season identity is inconsistent with the schema's own documentation.** `seasons.name` is commented as `"2025/2026"` but `upsertSeason` writes the bare provider year (`"2025"`), and `syncStandings` then does `Number(season.name)` to get back to it. Pick one representation and store the provider year in a dedicated integer column. **Small.** **RESOLVED (2026-08-18):** `seasons.provider_year` is now a dedicated integer column (see `upsertSeason` in `src/lib/football/sync.ts`), with `name` kept as the display string.

31. **Add `pg_trgm` GIN indexes for the three `ilike '%...%'` searches** on `teams.name`, `players.full_name`/`known_as`, and `competitions.name`. The existing btree indexes cannot serve a leading-wildcard match, so the command palette and fantasy player picker do sequential scans. **Small.** **RESOLVED (2026-08-18):** migration `0021_search_and_query_performance_indexes.sql` adds `pg_trgm` GIN indexes for the team/player/competition name searches.

32. **Index `transfers.from_team_id` and `transfers.to_team_id`.** Migration 0006 indexes only `player_id` and `transfer_date`, but the player page and any future club transfer ledger join on both team FKs. **Small.** **RESOLVED (2026-08-18):** migration `0021_search_and_query_performance_indexes.sql` adds `idx_transfers_from_team_id`/`idx_transfers_to_team_id`.

33. **Add a partial index for the Live page:** `create index on fixtures (kickoff_at) where status in ('live','halftime')`. The `/live` query filters on exactly that. **Small.** **RESOLVED (2026-08-18):** migration `0021_search_and_query_performance_indexes.sql` adds `idx_fixtures_live_kickoff on fixtures (kickoff_at) where status in ('live','halftime')`.

34. **Add `reports (status, created_at)`** to serve the moderation queue's oldest-first filter on open statuses. **Small.** **RESOLVED (2026-08-18):** migration `0021_search_and_query_performance_indexes.sql` adds `idx_reports_status_created_at on reports (status, created_at)`.

35. **Add `standings (season_id, position)`** for the ordered table reads on `/leagues/[id]` and Match Centre. **Small.** **RESOLVED (2026-08-18):** migration `0021_search_and_query_performance_indexes.sql` adds `idx_standings_season_position on standings (season_id, position)`.

36. **Replace the client-side XP sum with an RPC.** Both `/home` and `/rewards` pull every `xp_ledger` row and reduce in JavaScript. A `get_xp_total()` `SECURITY DEFINER` function returning a single integer is one round trip and scales. **Small.** **RESOLVED (2026-08-18):** migrations `0023_xp_total_and_sync_run_pruning.sql`/`0025_...` add a `SECURITY DEFINER` `get_xp_total()` RPC, used by `/home`, `/rewards`, `/profile`.

37. **Replace the two-step social feed aggregate with one RPC or view.** `social/page.tsx` fetches 50 posts, then fetches every `like` reaction for those 50 ids, then builds a Map. A `posts_with_like_counts` view (or an RPC taking the viewer's profile id) returns count plus `liked_by_viewer` in one query. **Small.**

38. **Tighten the `notifications_update_own` policy.** The migration itself flags that RLS is row-scoped, so a user can rewrite their own notification's `payload` and `type`. Drop the UPDATE policy and expose a `mark_notifications_read(uuid[])` RPC instead. **Small.** **RESOLVED (2026-08-18):** migration `0019_security_hardening_recs_38_39_42.sql` drops `notifications_update_own` and adds a `mark_notifications_read(uuid[])` RPC that only sets `read_at`.

39. **Escape user input before building `ilike` patterns.** `searchPlatform` and `searchFantasyPlayers` interpolate raw query text into `%${q}%`. A user typing `%` or `_` gets wildcard semantics, and a string of `%` characters is a cheap way to force expensive scans. Escape `%`, `_` and `\`. **Small.** **RESOLVED (2026-08-18):** `src/lib/text.ts`'s `escapeLikePattern` escapes `%`, `_`, `\` and is applied in `players/actions.ts`, `fantasy/actions.ts`, `search-actions.ts`.

40. **Validate route params as UUIDs before interpolating them into PostgREST filters.** `teams/[id]/page.tsx` builds `.or(\`home_team_id.eq.${id},away_team_id.eq.${id}\`)` directly from the URL segment. Even though a malformed value will error rather than leak, unvalidated input inside a filter-expression string is the wrong default. Add a shared `parseUuidParam()` that calls `notFound()` on a bad shape. **Small.** **RESOLVED (2026-08-18):** `src/lib/params.ts`'s `parseUuidParam()` is used by `teams/[id]`, `managers/[id]`, `venues/[id]` (and comparable detail routes) before interpolating into filters.

41. **`redeem_invite_code` returns raw Postgres error text to the client.** `joinFantasyLeague` passes `error.message` straight through. That is correct for the function's own `raise exception` messages but leaks internals for any other failure (constraint violations, type errors). Match on a known set and fall back to a generic message otherwise. **Small.** **RESOLVED (2026-08-18):** `joinFantasyLeague` now matches against a fixed `KNOWN_REDEEM_INVITE_CODE_ERRORS` set and falls back to a generic message otherwise.

42. **Six-character invite codes have no redemption throttle.** The alphabet is 32 characters and the code is 6, so the space is about 1e9, which is fine against a single attacker but not against an unthrottled server action. Add per-user attempt limiting inside the RPC. **Small.** **RESOLVED (2026-08-18):** migrations `0019_security_hardening_recs_38_39_42.sql` and `0024_redeem_invite_code_durable_throttle.sql` add a durable 5-attempts/60s throttle inside `redeem_invite_code` itself.

43. **Public fantasy leagues cannot be discovered.** `fantasy_leagues.is_private` exists and the UI offers a Private/Public toggle, but there is no browse-public-leagues surface and `redeem_invite_code` requires a code regardless. Either ship discovery for public leagues or remove the toggle rather than shipping a switch that changes nothing. **Medium.** **RESOLVED (2026-08-18):** migration `0027_public_fantasy_league_discovery.sql` adds `list_public_fantasy_leagues`/join RPCs; `fantasy/browse/public-leagues-list.tsx` ships the browse surface.

44. **`follows.followed_id` is polymorphic with no FK and no cleanup.** Deleting a team leaves dangling follow rows that will render as broken links once a followed-entities page exists (item 13). Add a cleanup trigger or a periodic admin-triggered reconciliation. **Small.** **RESOLVED (2026-08-18):** migration `0020_follows_cleanup_and_predictions_fixture_restrict.sql` adds a cleanup trigger that deletes dangling `follows` rows when a followed entity is deleted.

## 7. Accessibility

143. **Both tab groups lack ARIA semantics.** `MatchCentreTabs` and the fantasy Squad/Leaderboard switcher are plain `<button>`s with no `role="tablist"`, `role="tab"`, `role="tabpanel"`, `aria-selected` or arrow-key navigation. Screen reader users get three unlabeled buttons. **Small.**

144. **Match Centre's active tab is not in the URL.** It cannot be shared, bookmarked, or survive a refresh, and the browser back button does not undo a tab change. Use a search param. **Small.**

145. **The command palette has no combobox semantics.** No `role="listbox"`, no `role="option"`, no `aria-activedescendant`, so keyboard arrow navigation moves a visual highlight that assistive tech cannot see. **Small.**

146. **The keyboard-active palette result is never scrolled into view.** Arrowing past the fifth result in a `max-h-80` container moves the selection off-screen. **Small.**

147. **The notification panel declares `role="dialog"` with no focus trap and no focus return.** `MobileBottomNav` implements a proper trap and could be the shared reference. **Small.**

148. **`PlayerActionSheet` and `PlayerPicker` declare `role="dialog" aria-modal="true"` with no focus trap, no Escape handler, and (for the action sheet) no `aria-label`.** `aria-modal` without a trap is an active lie to assistive tech, which is exactly the reasoning already written into `mobile-bottom-nav.tsx`. Extract that trap into a shared `useFocusTrap` hook and apply it to all four dialogs. **Small.**

149. **Full-screen backdrop `<button aria-label="Close">` elements** are announced before the dialog content in three sheets. Use a non-focusable div with a click handler plus an explicit close button. **Small.**

150. **Standings render as CSS grids of `<span>`s,** not tables, so they carry no row or column relationships. The admin users table gets this right with real `<th>`. Use a real `<table>` with `scope` attributes. **Small.**

151. **Match result colour is the only encoding of win/loss.** `teams/[id]` colours a scoreline green or red with no accompanying W/L text, which fails for colour-blind users. **Small.**

152. **`text-[9px]` and `text-[10px]` appear throughout** (nav labels, badge chips, standings headers, stat captions). Below roughly 12px, legibility drops sharply on real phone screens. Raise the floor. **Small.**

153. **`html { font-size: 17px }` in `globals.css` overrides the user's browser base font size.** Anyone who has increased their default text size gets it silently ignored, which is a WCAG 1.4.4 problem. Use `font-size: 106.25%` (or bump the Tailwind type scale) to keep the intended visual size while respecting user preference. **Small.**

154. **No `color-scheme: dark` declaration.** Native controls, including the `<select>` in the fantasy create-league card, render with light chrome on a dark page. The `className="bg-kivo-navy"` on `<option>` elements is ignored by most browsers, so that dropdown is likely white-on-white somewhere. **Small.**

155. **The reduced-motion block clamps `transition-duration` globally with `!important`,** which also kills useful non-motion transitions like colour and opacity changes on hover and focus. Narrow the rule to `animation` and transform-based transitions. **Small.**

156. **Focus rings are inconsistent.** Present on nav links, palette results, `PostCard`'s like button and `FollowButton`; absent on `MatchCentreTabs`, the fantasy view tabs, `PlayerToken`, `ActionRow`, `InlineSyncButton`, `FootballSyncButton` and the report row buttons. **Small.**

157. **No `aria-live` on async result regions:** AI chat messages, prediction errors, post errors and the fantasy save bar all appear silently. The sync buttons get this right with `role="status"`. **Small.**

158. **Pending buttons set only `disabled` and an opacity change,** with no `aria-busy`. **Small.**

159. **`.kivo-glass:hover` applies a background change to non-interactive cards,** so static containers (fixture list items, stat panels) signal clickability they do not have. Scope the hover to an opt-in class. **Small.**

## 8. New features, real data only

160. **Team form guide (last five results).** Derived entirely from `fixtures` rows already fetched by `/teams/[id]`, which currently queries the last ten finished matches and shows them as a list without the at-a-glance W/D/L strip every competitor has. Zero new queries, zero new quota. **Small.**

161. **Head to head.** Real: query `fixtures` for prior meetings between two teams and show the record. Appears on Match Centre and on team pages. Honest fallback when KIVO has fewer than N synced meetings: say exactly how many it has. **Small.**

164. **Club transfer ledger.** All transfers in and out for a club, from the `transfers` table joined on `from_team_id`/`to_team_id`. No extra provider calls, and it makes the transfers already synced far more useful. **Small.**

170. **Fan match ratings.** Users rate a performance after the whistle. New table, RLS mirroring `predictions`, aggregate via RPC. **Medium.**

171. **Post-match fan verdict.** Aggregate of item 170 plus match-room reaction counts, rendered as a shareable card. Real user data end to end. **Medium.**

172. **Poll posts.** A post type with two to four user-authored options and real vote counts. Pure user-generated content, no football data dependency, and it works today with zero synced fixtures. **Medium.**

173. **Saved posts and player/team watchlists.** `follows` already models the polymorphic pattern; a `saves` table mirrors it. **Small.**

174. **"Your matchday" module on Home.** Filter today's fixtures to the user's `follows` plus `favourite_team_id`. This is the payoff that makes items 12 and 13 worth doing, and it needs no new data. **Medium.**

177. **News: keep it Coming Soon or source it honestly.** There is no news source in the stack and API-Football does not provide one. The only honest options are official club and league RSS feeds with visible attribution and links out, or leaving the surface as-is. ## 9. AI Copilot

182. **Resolve followed entities to names in the grounding context.** `buildGroundingContext` currently tells the model "Follows 5 team(s)/player(s)/competition(s) (internal IDs only, no names resolved here)", which is close to useless: it costs tokens and conveys nothing actionable. Join to the entity tables and list the actual names. **Small.**

183. **`hasFollowedEntities` and `hasSyncedFixtures` are computed and never used.** They are returned from `buildGroundingContext` and dropped. Use them to change the UI: swap the suggestion chips, and label the input honestly when nothing is synced. **Small.**

184. **Add fixture-scoped grounding.** An "Ask about this match" entry point on Match Centre that grounds on that fixture's real events, lineups and standings. This is where the grounded-AI pattern is most valuable and where the data is densest. **Medium.** **Status: DONE (2026-08-15).** `AskAiLink` (`src/components/ai/ask-ai-link.tsx`) on Match Centre deep-links to `/ai?ctx=fixture&id=<id>`; `src/lib/ai/grounding.ts`'s `buildGroundingContext` now accepts an optional `GroundingFocus` and, for a fixture, grounds on real teams/competition/kickoff/status plus H2H/form via `buildMatchInsights` (reused, not reimplemented) — not lineups/standings specifically, since Match Intelligence already covers the higher-value H2H/form/goal-timing surface and re-deriving a separate lineups/standings grounding path was judged lower value for this pass's scope.

185. **Add team- and player-scoped grounding** from the entity pages, using the same real rows those pages already render. **Medium.** **Status: DONE (2026-08-15).** Same mechanism as 184 — `AskAiLink` on `teams/[id]` and `players/[id]`, grounding on the real team/player name plus real last-5 form via `computeTeamForm`/`computePlayerForm` (the exact functions those pages already call, not reimplemented). The focus is resent by the client on every turn of a session that started from a deep link (see `chat.tsx`'s `focus` state), not persisted server-side against the conversation row — an acceptable, honest trade-off for this pass: the alternative was a new `ai_conversations` column purely to carry a UI concern, which felt like schema growth for a client-state problem.

186. **Give the model read-only tools instead of one fixed pre-fetch.** The current design retrieves a fixed context before every call, so a question about a team the user did not follow gets "KIVO doesn't have that" even when the row exists. Anthropic tool use with a small set of grounded, RLS-respecting readers (`getTeam`, `getFixture`, `getStandings`, `getPlayerStats`) keeps the honesty guarantee (the tools can only return real rows) while massively widening what the Copilot can correctly answer. **Large.**

    **Scoping note (2026-08-15, explicitly not built this pass — flagged Large by design):** the core change is swapping `/api/ai/chat/route.ts`'s single `anthropic.messages.stream({..., system: [SYSTEM_PROMPT, groundingSummary]})` call (one fixed retrieval before the model ever runs) for a tool-use loop: define 4-5 narrow read-only tools (`getTeam(teamId)`, `getFixture(fixtureId)`, `getStandings(competitionId)`, `getPlayerStats(playerId)`, maybe `searchEntities(query)` for name resolution since the model won't have ids up front), each backed by a thin wrapper around queries this codebase already runs elsewhere (team page's own fetch, `form-engine.ts`, `match-intelligence.ts`) so no new data-access logic is needed, only new call sites. The loop itself: send the system prompt + tools array, read the response for `tool_use` blocks, execute the matching real Supabase query server-side (still RLS/service-role scoped exactly like today, so a tool can never return a row the user couldn't already see), append a `tool_result` message, and re-call the model — repeat until it stops requesting tools, with a hard cap (e.g. 4 rounds) so a confused model can't loop forever. What'd need to change concretely: (1) the streaming shape — today's single NDJSON stream over one `messages.stream()` call becomes a stream-then-pause-then-stream-again shape across tool rounds, which changes the client contract in `chat.tsx` (a `tool_call` frame type would need to exist so the UI can show "checking standings…" rather than going silent mid-turn); (2) cost — each tool round is a full extra model call, so `AI_CHAT_DAILY_MAX_REQUESTS`'s $0-budget-mindset cap (item 190) would need re-tuning against a variable-not-fixed number of model calls per user turn, not the current one-call-per-message assumption; (3) the honesty guarantee shifts from "the context handed to the model is exhaustively pre-verified" to "every tool result is verified, but the model chooses which/how many to call" — still honest (a tool can only return real rows, same as today's pre-fetch), but it's a different failure mode to reason about (a model that *doesn't* call a tool it should have, versus today's model that never had the option); (4) provenance tagging (item 188, shipped this pass) would need to move from "one system-prompt instruction covering a static context block" to something that survives a multi-turn tool loop — likely tagging at the tool-result-append step rather than trusting the model to keep tagging correctly across rounds. Rough risk: medium-high — this is the single biggest architectural lever left in the Copilot, but it's also the one most likely to introduce a real regression (a tool-use loop that never terminates, or a provenance tag that silently stops appearing) if rushed, which is exactly why AGENTS.md flagged it out of this pass rather than asking for a rushed version.

187. **Stream the response.** A 1024-token answer currently appears all at once after a multi-second wait behind three bouncing dots. Streaming is the single biggest perceived-quality improvement available in the chat. **Medium.**

188. **Render provenance explicitly.** The system prompt already asks the model to distinguish verified KIVO data from general knowledge from inference. Have it tag claims and render those tags as visible chips. That turns an invisible prompt rule into a visible product promise. **Medium.** **Status: DONE (2026-08-15).** `grounding.ts`'s summary is now built as two explicitly labelled sections, "VERIFIED KIVO DATA" (raw provider facts) and "KIVO-CALCULATED" (Form Engine/Match Intelligence derived stats) — a structural distinction, not just an instruction. `SYSTEM_PROMPT` (`/api/ai/chat/route.ts`) tells the model to prefix a sentence citing either section with the literal inline tag `[[KIVO-VERIFIED]]`/`[[KIVO-CALCULATED]]`; `chat.tsx`'s `renderMessageContent` turns a tag into a small visible chip (cyan "Verified" / violet "KIVO-calculated") and degrades honestly to plain text if a given reply never uses a tag — nothing breaks, no chip fabricated.

189. **Add a "what KIVO knows right now" disclosure panel** showing `grounding.summary` verbatim. The most honest possible AI interface is one that shows the user its entire context window of facts. **Small.** **Status: DONE (2026-08-15).** A collapsed-by-default panel (toggle via the header's info icon) in `chat.tsx` shows `grounding.summary` verbatim in a scrollable monospace block — the literal string the model receives, not a separately hand-built summary that could drift from reality — plus a freshness line reusing `getTransparencyFreshness()` (the same helper `/transparency` already uses) for "last provider sync" / "quota remaining today", per AGENTS.md's instruction to reuse that logic rather than rebuild it.

190. **Cap cost per user.** No rate limit, no daily message cap, no token accounting. One scripted client can burn the Anthropic budget. Persist token usage per conversation from the response and enforce a daily ceiling. **Small.**

191. **Cache the system prompt.** It is long and constant across every request; prompt caching cuts real cost per call. **Small.**

192. **The chat input is an `<input>`, not a `<textarea>`.** Long questions scroll horizontally and Shift+Enter cannot add a newline. **Small.**

193. **The message list never auto-scrolls to the newest message.** **Small.**

194. **No copy button, no regenerate, no timestamps** on assistant messages. **Small.**

195. **Suggestion chips are hardcoded** and include "What data does KIVO have synced today?", which is a good question the app could answer without the model at all. Make the chips reflect actual state. **Small.**

196. **`AI_MODEL` is read from the environment in `lib/ai/client.ts` but appears in neither `.env.example` nor `ENVIRONMENT.md`.** Undocumented environment variables are how staging silently runs a different model from production. **Small.**

197. **A fantasy assistant is the strongest grounded use case available.** Grounded strictly on the user's own roster, real prices, real fixture schedule and real synced form, with a hard rule against projecting points it cannot compute. Blocked on items 1, 2 and 5. **Large.**

    **Scoping note (2026-08-15, explicitly not built this pass — flagged Large by design):** still genuinely blocked on items 1/2/5 as written — `seasons.is_current` now gets set (item 1 shipped an earlier pass), but `fantasy_gameweeks` is still never inserted and `fantasy_points` is still never written (confirmed against current `src/lib/fantasy-scoring.ts` and the fantasy app routes before writing this note, not assumed stale), so there is no real scored-points data to ground an assistant's "how am I doing" answers in yet — building the assistant first would mean either grounding it in nothing (dishonest) or inventing plausible-looking projections (exactly the fabrication this codebase's standing rule forbids. What this would look like once unblocked: a fourth `GroundingFocus` type (`"fantasy_roster"`), entry point on `/fantasy`'s squad view, grounding on the user's own real roster (`fantasy_rosters`), real player prices already synced, the real upcoming fixture for each rostered player's team (reusing `fixtures` the same way `grounding.ts`'s today's-fixtures block already does), and each player's real recent form (`computePlayerForm`, already reused twice this pass for items 184/185/227 — a fourth reuse, not a new computation). The one genuinely new rule needed beyond what 184/185's pattern already provides: an explicit system-prompt instruction that the model may describe a player's real recent scoring history but must never state a specific *projected* fantasy-points number for an upcoming gameweek, since `fantasy_points` scoring is itself not written yet (item 5) and even once it is, a future score is inherently not a "real synced fact" the way a past one is — this is a new kind of honesty boundary the existing grounding architecture (185/188/189, all shipped this pass) doesn't yet need to express, since everything grounded so far is either a past fact or a present one. Rough risk: low-medium once items 2 and 5 land (the grounding pattern itself is now proven three times over); the real blocker is genuinely upstream, not this item.

## 10. Security and abuse resistance

198. **Nothing in the application is rate limited.** Not `/api/ai/chat` (real dollar cost per call), not `createPost`, not `toggleLike`, not `toggleFollow`, not `submitPrediction`, not `setGameweekRoster`, not `joinFantasyLeague`, and not `searchPlatform`, which is callable by unauthenticated guests. The prior log deferred this pending an Upstash decision; it should not survive to a public launch. If adding Redis is unacceptable, a Postgres-backed sliding window keyed on profile id is workable at MVP scale. **Medium.**

199. **`searchPlatform` is the most exposed endpoint in the app:** a guest-callable server action running three unindexed `ilike '%...%'` scans per keystroke-debounce, with wildcards unescaped. Combine items 31 and 39 with a rate limit and a length cap. **Small.**

200. **`ensureFantasyPlayerPrices` lets any signed-in user drive service-role writes.** It is called from `searchFantasyPlayers` on every debounced keystroke and upserts a row per returned player using the RLS-bypassing client. Cap the batch and skip the write when every returned id already has a price. **Small.**

201. **No security headers.** `next.config.ts` sets only image remote patterns. Add a CSP, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy` and `X-Content-Type-Options`. **Small.**

202. **Clerk's `user.deleted` webhook hard-deletes the profile,** cascading away every post, comment, prediction, fantasy team, XP row and badge with no export and no tombstone. That is defensible as a privacy stance but should be a deliberate, documented decision, and orphaned social threads will lose their parent posts. **Medium.**

203. **`user.updated` overwrites `display_name` and `avatar_url` from Clerk unconditionally.** Harmless today because KIVO exposes no editor for either, but it will silently revert user edits the moment item 16 ships. **Small.**

204. **Every failure path is `console.error`.** No Sentry, no structured logging, no request correlation. In a serverless deployment these are effectively write-only. **Small.**

Must be suppressed below a minimum total-roster sample size (mirroring item 168's own suppression rule) so early on, with a handful of KIVO users, a single person's pick never renders as a meaningful "5% ownership" differential. **Medium.**

251. **Make fantasy pricing genuinely dynamic instead of a permanent flat 5.0 for every player.** Migration `0007_fantasy_player_pricing.sql`'s own comment is explicit that every player currently gets an "identical flat, clearly-arbitrary starting price" because there was no real performance history to derive one from at the time it was written — but `fantasy_points` (item 5) is now real and scored. A price-adjustment pass keyed on real recent fantasy-points delta (e.g., nudge price up/down by a small bounded amount per gameweek based on real over/under-performance relative to the player's position-group average, the same position-aware convention `rating-engine.ts` already established) turns the pricing system from a decoration into a genuine, data-grounded game mechanic — the actual differentiator that makes a "differentials" view (item 250) and a real squad-value strategy meaningful, the way FPL's own pricing works. Must stay clearly labelled as KIVO's own internal game currency, never real market value (per migration 0007's own explicit non-claim), and any adjustment must be a small, capped, transparent delta with its formula documented in the UI (the same "publish the scoring rules" discipline item 5 already applied to gameweek scoring), not an opaque number that moves for reasons a user can't see. **Large.**

252. **A gameweek review page: real top scorers and real "most captained" percentage.** Once a gameweek is scored, show "Top scorers this gameweek" (real `fantasy_points` sorted) and "X% of KIVO managers captained [Player]" (real aggregate over `fantasy_rosters.is_captain` for that gameweek, same ownership-aggregation mechanism as item 250) — this is the single highest-engagement page on every real fantasy platform and needs no new data, only a new read and a new route. Suppress the captaincy percentage below the same minimum-sample threshold as items 168/250. **Small to Medium.**

### Social and community depth

253. **Club-specific community hubs.** `posts.fixture_id` already exists and is fully wired for match-scoped rooms (item 8), but there is no club-scoped equivalent — a Manchester United fan currently has no single feed of everything KIVO-native about that club (posts, match rooms for their fixtures, transfer activity, upcoming matchday). This needs one real schema addition, `posts.team_id` (nullable, same polymorphic-adjacent pattern `follows.followed_id` already uses, but as a proper FK this time since a post about a specific club has exactly one club, not an ambiguous type), a compose-time "tag this post to a club" affordance, and a `/teams/[id]` "Community" tab aggregating: real team-tagged posts, links to that team's real upcoming Match Rooms, and the team's real recent transfer activity (already synced, item 164). This is the single largest genuine community-depth gap relative to what the landing page already promises about Match Rooms — it extends the exact same pattern to the club level instead of only the fixture level. **Large.**

254. **System-authored live event posts inside Match Rooms.** When a real goal or red card lands via `sync-match-details.ts`'s `upsertFixtureEvent` (the same trigger `match-notifications.ts` already hooks for push-adjacent notifications, item 60's real-time producers), also insert a system-authored post into that fixture's Match Room ("⚽ GOAL — [Player Name], 67'") — turning the room from a place users have to remember to post in themselves into one that's alive automatically, seeded entirely by real, already-synced events. Must be visibly distinguished from user posts (a "KIVO" system badge, not a fabricated persona pretending to be a fan) so users are never misled about who's actually posting. **Medium.**

255. **Admin data-quality tooling: duplicate-entity detection and missing-asset reporting.** `BUILD_STATUS.md`'s own Admin row names this directly as a real, confirmed gap — "data-quality tooling (duplicate detection, missing-logo detection) doesn't exist yet." Concretely: a Data Health panel listing teams/players whose names are suspiciously close (Levenshtein distance under a threshold, or two different `provider_mappings` rows that plausibly point at the same real-world entity across a provider switch) for a human to merge, plus a simple count of teams with a null `crest_url` and players with a null `photo_url` so an admin knows where the visual gaps are before a user finds them. Entirely a data-integrity tool, produces no new user-facing claims. **Medium.**

### Personalization and discoverability

256. **Rank the home feed / social feed by genuine affinity, not just recency.** Today's Home page (`home/page.tsx`) is real but purely rule-based (today's fixtures, matchday fixtures for followed teams, upcoming fixtures for followed teams) with no blended, ranked "for you" surface mixing football and community content, and `/social`'s feed is a flat, unranked `limit(50)` by recency. A genuine personalization pass would blend: real fixtures for followed/favourite teams, real posts tagged to those teams (once item 253 ships) or authored by followed users, and real Match Rooms for today's followed-team fixtures — ranked by a transparent, explainable real-data formula (recency + follow-affinity, e.g. a followed team's post outranks a random one only because of the real `follows` row, not an opaque engagement-maximizing score). The explicit constraint from the brief applies directly here: no fabricated engagement signals, no invented "trending" without a real time-windowed event log to back it (the same honesty reasoning item 61's "Popular teams" label — not "Trending" — already established for search). **Large.**

257. **Follow suggestions from real co-follow and competition adjacency.** "Fans of [followed team] also follow" is real, computable data once KIVO has enough `follows` rows (a simple co-occurrence count: which other teams are followed by users who follow team X), and "Other clubs in [followed team]'s league" is a zero-inference join through `standings`/`seasons`. Both are honest, real-data suggestions — explicitly do not fabricate a "recommended for you" score when the underlying co-follow sample is too small; fall back to the competition-adjacency version (always available once any competition has 2+ synced teams) rather than showing nothing. **Small to Medium.**

258. **Cross-entity related links.** Team pages currently link out to very little beyond their own squad — no "rivals" (derivable honestly from H2H frequency: teams KIVO has synced the most real prior meetings against), no "recent transfer connections" (clubs a team has actually bought from/sold to, from the real `transfers` table, item 164's ledger), no squad-mate cross-links from a player page back to teammates who've actually appeared alongside them in synced `lineups`. All are pure joins over data already in the schema; the value is entirely in surfacing connections a user would otherwise have to navigate to manually. **Small.**

259. **Upgrade search from `ilike` scans to real Postgres full-text search, and widen its scope to fixtures and posts.** Item 31 already added `pg_trgm` indexes for speed; this item is about *relevance*, a different axis — a `tsvector` column with `to_tsquery`/`ts_rank` would let "arsenal liverpool" match a fixture between those two teams and rank a well-known club above a lesser-known one with a substring match, neither of which plain `ilike` scoring can do. Also widen `searchPlatform`'s scope: today it searches teams/players/competitions only, with fixtures (searchable by team-name-plus-date) and posts (searchable by body text) both real, already-indexed data the command palette never reaches today. **Medium.**

### Retention (honest) and internationalization

260. **A concrete badge catalogue expansion tied to genuinely tracked actions.** Item 140 already flagged the two-entry badge catalogue as the cheapest engagement surface in the product; this item makes it concrete rather than leaving it as a generic "add more" note. Real, already-measurable candidates: a "Derby Day" badge for posting in N different fixture-scoped Match Rooms (real, once item 8's Room tab usage accumulates), a "Scout" badge for using the comparison pages (items 244/245) a set number of times, a "Prediction Streak" badge tied to the real streak data `streak.ts`/`get_activity_streak()` already compute, and a "Community Voice" badge for real comment-thread participation (item 7's shipped comment UI). Every criterion must be a real, already-queryable count — no badge should exist whose award condition can't be answered by a single SQL query against a real table today. **Small.**

261. **A weekly recap page, not a push notification (no push infra exists, confirmed in `BUILD_STATUS.md`).** A `/rewards`-adjacent "Your week" view aggregating real numbers already computed elsewhere in the codebase: XP earned this week (`xp_ledger`, already summed via `get_xp_total`), prediction accuracy this week (real, once item 3's scoring exists), fantasy points this gameweek, and the current activity streak (`streak.ts`) — a single honest, non-manipulative "here's what you actually did" summary, the same spirit as `RECOMMENDATIONS.md` item 176's "what KIVO knows" transparency page applied to a user's own activity instead of the platform's data coverage. No artificial urgency framing, no "you're missing out" dark-pattern copy — purely a real recap. **Medium.**

Full multi-language i18n (a translation layer, a language switcher) is a much larger, separately-scoped investment with no evidence yet that it's the actual gap — flagging the timezone/locale-consistency half as the real, cheap, honestly-scoped piece of this, and explicitly not proposing a fabricated "12 languages supported" claim or building translation infrastructure speculatively ahead of a real, stated multi-market requirement. **Small for the audit; Large if full i18n is later decided as a real requirement.**

## 17. 2026-08-18 Frontend, design & structure recommendations sweep

A fresh pass over the actual component code — `src/components/` across every area, every page under `src/app/(app)/`, and the design tokens in `globals.css` — specifically for where the established glass/pill/underline-tab language is thin or inconsistent, plus genuinely new structural patterns. Every item below is grounded in a specific file read tonight, not a generic design checklist. Confirmed first: KIVO is dark-only on purpose (`color-scheme: dark` is a static declaration in `globals.css`, not a media query; there are no light-mode token values anywhere in `:root`) — see item 280 for the explicit reasoning on whether that should change.

### Desktop and tablet layout

263. **A `max-w-2xl` ceiling caps nearly every page in the app, including on a full desktop monitor.** Grepped across `src/app/(app)`: 25 page/component files constrain their root container to `max-w-2xl` (42rem/672px) — `/matches`, `/predictions`, `/transfers`, `/notifications`, `/settings`, `/saved`, `/u/[username]`, `/players/compare`, the fantasy builder, and more (their matching `loading.tsx` skeletons follow the same width, so at least that part is consistent). `DesktopSidebar` (`src/components/layout/desktop-sidebar.tsx`) reserves a real 256px rail and the app shell has the width to spare beyond that, but content still renders as a stretched mobile column with wide empty gutters on either side at any viewport past roughly 1000px. Only Home breaks the pattern at `max-w-5xl` (`src/app/(app)/home/page.tsx`). This isn't a call to fill the space with clutter — it's the clearest opportunity in the app to add a real desktop-only secondary rail (a live-scores strip, a "your teams" module, related content) on the pages that would benefit most, rather than the same single centered column at every viewport from 375px to 2560px. **Medium** (a layout primitive plus per-page decisions on what, if anything, fills the rail).

264. **The `md:` Tailwind breakpoint (768–1023px) is used nowhere in the codebase — confirmed by grep returning zero files — and `xl:` is equally unused.** Only `sm:` (640px, 35 files) and `lg:` (1024px, 66 files) appear anywhere. That means the entire 640–1023px band — portrait iPad, most Android tablets, a browser window in split-view — gets whichever styles apply at `sm:` and never anything tuned in between, right up until the desktop sidebar snaps in at exactly 1024px. Concretely, `TeamsGrid` (`src/components/teams/teams-grid.tsx`) is `grid-cols-2 sm:grid-cols-3` with no `lg:` bump, so a 9.7" iPad in portrait — nearly 2.5x a phone's width — still renders the exact same 3-column crest grid it would at 640px. Worth an explicit tablet pass: pick 2–3 components (browse grids, the match centre stat tables, the fantasy pitch) and give them one `md:` step instead of jumping straight from phone-width to the full three-pane desktop shell. **Medium.**

265. **`TeamsGrid` never grows past 3 columns, at any width.** `src/components/teams/teams-grid.tsx:70` is `grid grid-cols-2 gap-3 sm:grid-cols-3` with no `lg:`/`xl:` step, and it renders inside `EntityListPage`'s `max-w-2xl` shell (item 263) regardless. A crest grid is exactly the kind of content that should use extra width when it's available — more columns, not more whitespace. **Small.**

266. **The fantasy squad builder — the single most complex interactive tool in the app — is confined to the same `max-w-2xl` column as a settings page.** `src/app/(app)/fantasy/fantasy-builder.tsx:286` roots the whole builder (pitch view, bench, budget bar, player picker) at `max-w-2xl`, and the sticky action bar at line 563 explicitly caps itself to the same width even on `lg:`. A drag-to-build tool like this is the strongest candidate in the whole app for a real two-pane desktop layout — pitch/squad on one side, the player picker as a persistent side panel instead of the bottom sheet (`player-action-sheet.tsx`) it currently opens as on every viewport. The bottom-sheet picker is right for mobile; desktop deserves better than a wider version of the phone layout. **Large** (meaningfully different desktop and mobile layouts for one component).

267. **`/saved` has no entry point anywhere in navigation.** It's absent from `NAV_ITEMS` (`src/lib/navigation.ts`), so it appears in neither `DesktopSidebar`'s grouped list nor `MobileBottomNav`'s "More" sheet — grepped directly, the only `href="/saved"` in the entire `src/` tree is one small text link on `/profile` (`src/app/(app)/profile/page.tsx:164`). `SaveButton` (`src/components/ui/save-button.tsx`) is wired into player and team pages and clearly meant to be a real watchlist feature, but a user who saves something from a player page has no path back to their saved list except remembering to visit their own profile first. Add it to the "You" sidebar group and the mobile "More" sheet alongside Rewards/Settings/Profile. **Small.**

268. **`/discover` duplicates the sidebar's own "Explore" grouping instead of doing something the sidebar can't.** `SIDEBAR_GROUPS` in `desktop-sidebar.tsx` already groups Teams/Players/Leagues/Transfers under "Explore", permanently visible on desktop; `/discover`'s page (`src/app/(app)/discover/page.tsx`) is a card grid linking to those same four destinations plus a synced-row count each. On desktop the two are almost redundant. Discover is more valuable as a genuine cross-entity surface the sidebar can't be — search-driven recommendations, "trending this gameweek," recently-added entities — than as a second static directory of the same four links the sidebar already always shows. **Medium** (a product decision, not just a restyle).

### Motion and state transitions

269. **Lists that reorder — standings, leaderboards, live fixtures — have no shared-layout animation, so a rank change just jumps.** `StaggeredList` (`src/components/ui/staggered-list.tsx`) wraps each row in a plain `FadeIn` keyed by item id; it staggers *entrance* nicely but doesn't use Framer Motion's `layout`/`layoutId` on the rows themselves, so when row order actually changes — a live score updates and a team leapfrogs another in `StandingsTab` (`match-centre-tabs.tsx`), a fantasy or predictions leaderboard re-sorts after a scoring pass, a live fixture moves in `LiveFixtureList` — the DOM just re-renders in the new order with no visual continuity between "row was here" and "row is now here." `kivo-row-flash` already exists for *content* changes within a row; there's nothing equivalent for *position* changes. Adding `layout` to the row wrapper (Framer Motion handles the FLIP animation automatically) would make a standings shuffle after a live goal actually read as movement instead of a silent swap. **Medium.**

270. **`PageTransition` treats every navigation identically regardless of hierarchy direction.** `src/components/layout/page-transition.tsx` applies the same `opacity + y:8→0` slide on every route change — drilling from `/teams` into a specific team, going back up, or switching laterally between top-level nav items all get the exact same motion. A small directional distinction (forward/drill-in slides one way, back/up the other, lateral tab-style switches cross-fade only) is a well-established way to make navigation feel spatially coherent rather than every screen just being "the next thing that faded in." The comment on this file already explains a real, deliberate performance tradeoff (no `AnimatePresence` exit, to avoid the RSC-round-trip delay `mode="wait"` used to add) — this item is only about varying the *entrance* motion, not reintroducing that cost. **Medium.**

271. **The shimmer-to-content swap on every `loading.tsx` is an instant DOM replacement, not a cross-dissolve.** `Skeleton` (`src/components/ui/skeleton.tsx`) is a plain `animate-pulse` block; Next's `loading.tsx` convention means the moment real data resolves, React swaps the whole subtree in one render with no transition between the two states. Match Centre, standings, and the fantasy leaderboard all have real, well-built skeletons (per the 23 `loading.tsx` files already in the app) that currently just hard-cut to final content. A short opacity cross-fade at the swap point (even just wrapping the resolved content in `FadeIn`, which most pages already import) would soften what's currently a visible jump-cut on every single navigation into a data-heavy page. **Small** (mechanical, high-leverage given how many routes it touches).

### Data density and visual hierarchy

272. **Every row in the Match Centre Stats tab carries identical visual weight.** `StatsTab` in `match-centre-tabs.tsx` (`STAT_ROWS`, ~line 330) renders Possession, Shots, Shots on target, Corners, Fouls, Offsides, Yellow cards, Red cards, Pass accuracy, Saves, and xG as eleven visually uniform rows — same `text-xs`/`font-semibold` numbers, same bar height, same label size, top to bottom. A user scanning for "who's actually winning this match" has to read all eleven with equal effort; nothing distinguishes the stats a football fan actually leads with (possession, shots, xG) from the ones that are secondary context (offsides, fouls). A simple weight split — the 3–4 headline stats slightly larger/bolder with more bar height, the rest visually quieter — would let the tab guide the eye instead of presenting a flat list. **Small.**

273. **The Match Centre Standings tab shows only `#`/Team/P/GD/Pts — no W/D/L, no form guide — despite `FormBadges` already existing and being used on four other pages.** `StandingsTab` (`match-centre-tabs.tsx`) renders a bare 5-column table. `FormBadges` (`src/components/teams/form-badges.tsx`) — a real W/D/L pill strip driven by `FormResult`/`resultFor` — already ships on `/teams/[id]`, `/teams/compare`, `/players/[id]`, and `/managers/[id]`, so the data and the component both exist; Match Centre's own standings tab is the one natural fifth call site that's missing it. A trailing form-guide strip per row (even truncated to last-3 given the table's existing `min-w-[26rem]`) would turn a plain league table into the same "how are they trending" signal every other team surface in the app already gives. **Small.**

274. **Match Centre's own tab-level empty state is visually thinner than the rest of the app's empty-state language.** `EmptyState` (`match-centre-tabs.tsx:134`) — used when Details/Stats/Lineups/Standings haven't synced yet — is a bare centered text string in a plain `.kivo-glass` box, no icon. Compare that to `NoDataYet` (`src/components/ui/no-data-yet.tsx`, icon + title + description, deliberately "quieter than ComingSoon" per its own doc comment) or `ComingSoon` (`src/components/ui/coming-soon.tsx`, full gradient glow + 3D art treatment) — both considered, tiered empty states elsewhere in the app. Match Centre's version reads as an afterthought next to them, and it's one of the highest-traffic surfaces in the product (every unsynced or pre-kickoff fixture hits it on four separate tabs). Bringing it up to at least `NoDataYet`'s tier (a small icon, real title/description split) would close a real visible gap on a heavily-trafficked screen. **Small.**

### Accessibility depth

275. **No skip-to-content link anywhere in `AppShell`.** `src/components/layout/app-shell.tsx` renders `DesktopSidebar` before `TopBar`/`main` in DOM order, and `DesktopSidebar`'s own `<nav>` (`desktop-sidebar.tsx:43`) contains roughly 15 links across five groups before a keyboard or screen-reader user ever reaches page content — repeated on literally every page load, since there's no persistent "skip to main content" anchor. (The `SkipLink` component in `src/components/onboarding/onboarding-flow.tsx` is a "skip this onboarding step" button, unrelated to this — there is no bypass-navigation link in the actual sense WCAG 2.4.1 asks for.) A visually-hidden-until-focused link at the very top of `AppShell`, jumping to `<main>`, is the standard fix and would help every keyboard user on every single page, not just one flow. **Small.**

276. **`/matches/[id]` is the only entity detail page in the app with no `<h1>`.** Checked directly against every sibling: `/players/[id]`, `/teams/[id]`, `/venues/[id]`, `/managers/[id]`, and `/leagues/[id]` all correctly wrap the entity's name in an `<h1>` (e.g. `teams/[id]/page.tsx:359`). `/matches/[id]/page.tsx` renders both team names as plain `<span>` elements in the score header (lines ~298–306) with no heading at all — the first heading anywhere on the page is an `<h2>` for the "Share this match" card, more than 300 lines down (`matches/[id]/page.tsx:368`). A screen-reader user navigating by heading (a core, common navigation pattern) gets no page-identifying heading on arguably the single most important detail page in the product, and lands on an orphaned `<h2>` with no preceding `<h1>` in its subtree. Fix: wrap the fixture's "Home vs Away" label (visually hidden if the crest/score layout shouldn't visibly change) in a real `<h1>`. **Small.**

277. **The Standings table scrolls horizontally with no visual cue that there's more to scroll to.** `StandingsTab`'s wrapper (`match-centre-tabs.tsx`) is `kivo-glass overflow-x-auto rounded-2xl` around a `min-w-[26rem]` table — on a narrow phone this can require a horizontal scroll, but nothing signals it (no edge shadow, no fade). `globals.css` already has exactly the right technique built and proven elsewhere in the same file: `.kivo-ticker`'s `mask-image: linear-gradient(to right, transparent, black 10%, black 90%, transparent)` fades content at both edges. Reusing that same mask (or just a lighter one-sided version) on the standings/any other `overflow-x-auto` table would give a real, cheap "there's more here" affordance instead of a silently-scrollable box. **Small.**

### Icon and third-party visual consistency

278. **Lucide icon stroke-weight drifts inconsistently across the app, with no shared convention enforced.** Grepped every `strokeWidth=` prop in `src/components` and `src/app`: `1.75` is the clear house style (180 uses) but `2` appears 88 times across 42 different files, `2.5` appears 22 times, `1.5` appears 18 times, and there are stray `3` and `2.25` values too. This isn't a deliberate "small icons get more weight" rule — e.g. `settings/page.tsx` uses `1.75` for its inline `Mail`/`AtSign` labels and `2` for the sign-out button's `LogOut` icon a few lines later, with no visible reason for the difference. Icons sitting next to each other at slightly different weights is the kind of inconsistency that reads as "slightly off" without being obviously wrong. A lint rule (or a thin `<Icon>` wrapper defaulting to 1.75, explicit override only when truly justified) would lock in the convention that already mostly exists. **Small.**

279. **Clerk's `<UserButton>` and its popover render with flat, non-glass styling next to everything else in the chrome.** The `ClerkProvider` appearance config in `src/app/layout.tsx` sets real KIVO colors (`colorPrimary`, `colorBackground: "#0d1630"`, `borderRadius: "0.75rem"`) but there's no `backdrop-filter`/blur equivalent available through Clerk's variable API, and `0.75rem` is noticeably tighter than the `rounded-2xl`/`rounded-3xl` (1rem–1.5rem) used everywhere else. `TopBar` (`src/components/layout/top-bar.tsx:72`) drops `<UserButton />` in with no wrapper styling at all, right next to `NotificationBell`'s hand-built `kivo-glass-sharp` circular button. The account menu is one of the most-opened surfaces in the app (every session) and it's the one piece of chrome that visibly isn't KIVO's own glass language. Clerk supports custom component slots (`appearance.elements`) for exactly this — worth spending the effort to at least get the popover card onto `.kivo-glass-brand` and matching radius, even if the internal form controls stay Clerk-default. **Medium.**

### Dark mode

280. **Recommendation: do not build a full light mode — but a "true black" OLED variant is a much smaller, worthwhile alternative.** Confirmed directly: `color-scheme: dark` in `globals.css` is a static rule (not inside a `prefers-color-scheme` query), and there is not a single light-mode color value defined anywhere in `:root`. KIVO's entire depth system is built on glow-on-black — `.kivo-glass`'s translucency, every `kivo-aurora*` blob, `kivo-gradient-*` brand washes, `drop-shadow`/glow effects tuned against `--kivo-obsidian` (`#05060a`) — none of which reads the same way inverted onto a light surface; doing it properly would mean designing a second, parallel visual system (frosted-white glass, re-tuned glow opacities, a full contrast re-audit), not flipping a token file. Given the premium-dark, pump.fun-style identity this whole session has been building toward, that's very unlikely to be worth it. The smaller, genuinely worthwhile variant: a "true black" (`#000000` instead of `--kivo-obsidian`'s `#05060a`) toggle in Settings for OLED screens, which is a real battery/contrast win for a mobile-first product and needs only new token values, not a new system — explicitly framed as a variant of the existing dark theme, not a second theme. **Small** for the OLED variant; **Large** and **not recommended** for full light mode.

### New structural patterns

281. **A persistent live-score strip would put KIVO's real-time infrastructure to work outside of `/live` and `/matches/[id]`.** KIVO already has genuine realtime plumbing for this — live fixture subscriptions, `LiveFixtureList` (`src/components/matches/live-fixture-list.tsx`), and a purpose-built `kivo-row-flash` cue in `globals.css` for "this row just changed" — but all of that value is only visible to a user already sitting on the live page or a specific match's Match Centre. Browsing `/teams`, `/players`, or `/social` while a followed team is playing shows nothing. A collapsed pill anchored just above the mobile bottom nav (and as a slim bar under `TopBar` on desktop) showing 1–2 live fixtures for followed teams — score, minute, tap to expand into the full Match Centre — would be a genuinely new structural pattern rather than a visual tweak, and it's a natural extension of infrastructure that's already built rather than a speculative feature. **Large** (cross-page persistent state, real-time subscription lifted out of the live page, careful mobile real-estate budgeting against the bottom nav).

282. **The command palette (⌘K) is search-and-navigate only; extending it into a lightweight action palette would make it a genuine power-user surface.** `CommandPalette` (`src/components/layout/command-palette.tsx`) already does recent searches, entity search (teams/players/competitions), and section jump-links — real, working infrastructure. What it can't do yet is *act*: jump straight into "Compare players" with two names pre-filled, submit a quick prediction on today's fixture, jump to a specific fixture's Room tab, or (for an admin) toggle preview mode — all currently multi-click flows reachable only by navigating there manually. A small `actions` result group alongside the existing `teams`/`players`/`competitions` groups, reusing the same list/keyboard-nav UI already built, would turn an already-good search tool into the "everything, everywhere" surface top-tier platforms use ⌘K for, without touching its existing search behavior. **Medium.**

283. **A single Home-page or match-centre "this week's form" strip, reusing `FormBadges` across a user's followed teams.** Home (`src/app/(app)/home/page.tsx`) already builds a real "Your teams" module from `follows`; `FormBadges` (item 273) already exists and is proven on four pages. Neither currently reaches into the other — there's no single at-a-glance "how are the teams I follow trending right now" view, which is exactly the kind of glanceable, real-data summary a returning user opens the app to check. Small, high-leverage combination of two things that already exist rather than new data or new components. **Small.**

### Coverage gap

284. **Eleven routes have no `loading.tsx`, inconsistent with the pattern used everywhere else.** 23 routes already have a route-level `loading.tsx` with a tailored skeleton (confirmed by listing `src/app/(app)/**/loading.tsx`) — real, considered work, not a rubber-stamped pattern. Missing entirely: `/ai`, `/news`, `/notifications`, `/predictions/mine`, `/profile`, `/profile/following`, `/rewards`, `/saved`, `/settings`, `/teams/compare`, and `/u/[username]`. Several of these (Settings, Rewards, Profile) do real `Promise.all`-batched Supabase fetches on the server before first paint, so on a slow connection they're currently the one visible gap in an otherwise-consistent "shimmer while data streams in" experience — a blank flash where the rest of the app shows a skeleton. **Small** (mechanical, following the exact pattern the other 23 routes already establish).

## If you only do 10 things

Ordered by leverage, weighing "unblocks a whole feature" over "polishes a working one".

1. **Set `seasons.is_current` in the sync (item 1) and generate `fantasy_gameweeks` from real fixtures (item 2).** These two together unblock the entire fantasy product, the largest single body of code in the repo, which currently cannot be reached at all.

2. **Fix the guest author-name bug (item 20) with a public profiles view (item 21).** Every signed-out visitor currently sees "KIVO fan" on every post, on the platform's most public and most shareable surface.

3. **Ship prediction scoring plus the leaderboard RPC (items 3 and 4).** Predictions is a complete, working feature with no ending. Scoring turns a submission form into a game and feeds XP, badges and streaks for free.

4. **Add the report flow (item 6).** The moderation queue, urgency badges and audit trail are all built and can never receive a single item. This is a few hours of work that activates an entire admin surface, and it is a launch prerequisite for user-generated content.

5. **Build Match Rooms on `posts.fixture_id` (item 8).** The schema supports it, the landing page already sells it, and it is the differentiator the competitive research identified as the clearest greenfield opportunity. It also works with zero live data.

6. **Carry a redirect through every sign-up gate (item 102), and point the landing CTA at sign-up (item 103).** The cheapest conversion fix in the document: right now every gated action dumps the user on `/home` and the primary landing button converts nobody.

7. **Add `error.tsx`, per-route `loading.tsx`, and `generateMetadata` on the four detail routes (items 89, 90, 93).** Together these cover the three failure modes a real user hits first: a slow page, a broken page, and a shared link that looks like nothing.

8. **Cache `getOrCreateProfile` and the Supabase client per request, and suspend the notification fetch (items 78 and 79).** Every server render currently does the same auth and profile work two to four times and blocks the shell on a notifications query. This is a measurable latency win across the entire app for a very small diff.

9. **Fix the three real bugs: AI history order (item 19), fantasy position filter after limit (item 84), and the like-count revert (item 118).** All three are small, all three are currently wrong, and the first two make their features behave incorrectly rather than just imperfectly.

10. **Extract the duplicated primitives (`TeamCrest`, fixture status, `positionGroup`, `timeAgo`) and the sync mapping helpers (items 66 to 69, 29).** Eight copies of the same crest component and four copies of the same provider-mapping logic is the main structural debt in a codebase that is otherwise unusually well reasoned. Doing this now, while the copies are still identical, is an afternoon; doing it after they drift is a week.
